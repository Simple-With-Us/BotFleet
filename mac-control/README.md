# BotFleet Control

`BotFleetControl` is a small AppKit menu bar app for the local BotFleet Server.  It requires macOS 13 or newer, has no third-party dependencies, and does not start the server when launched.

Build and test with `swift build --package-path mac-control` and `swift test --package-path mac-control`.  The executable product is `BotFleetControl`.  Package it as `BotFleet Control.app` with bundle ID `app.botfleet.control.macos` and `LSUIElement=true`.  The app itself calls `NSApplication.setActivationPolicy(.accessory)`.

The menu checks `http://127.0.0.1:8799/api/health` for a ready BotFleet identity before reading or changing server state.  It reads `/api/system/control` when the menu opens.  “Start Local VM” is available when the shared VM is missing or newly created; a previously started and stopped VM needs recreation in BotFleet Computer settings.  Server and VM actions use the corresponding `/api/system/control/*` routes; changing “Keep Server Running After Quitting BotFleet” uses `PATCH /api/config`.  The app discards all other configuration data and does not log API bodies.

When the API is unavailable, the menu reads the installed `app.botfleet.server` LaunchAgent state.  An installed agent with no PID is shown as stopped and can be started with the installed versioned wrapper; an active but unresponsive agent is shown as unresponsive and cannot be started again from the menu.  A server that answers the health check as BotFleet but has no control routes is older than Control: the menu says so instead of calling it unresponsive, and “Stop Server And Local VMs…” then writes the deliberate-stop marker, boots the LaunchAgent out when its plist is installed, and watches port 8799 for twenty seconds, because the fenced stop route is what that server lacks and neither the bootout's exit status nor the plist proves the server is gone; a port that still answers is named, and so is a probe that could not tell.  The “Keep Server Running After Quitting BotFleet” toggle works offline through an atomic mode-0600 `persist-on-exit.policy` file containing only `true` or `false`; the server and Electron consume the same policy.  An absent file is shown as an unset local preference, not a guessed value.

The bundled `botfleet-vm-control.mjs` helper reports managed Local VM state and supports `create-stopped` and `stop` while the server is proven down.  Control invokes it with an installed Node binary and accepts only strict JSON success; the helper independently enforces the launchd, port, runtime, ownership, and label gates.  If that helper is unavailable, the menu can still show read-only Docker status after verifying a local Unix-socket context and exact BotFleet names and labels.  VM mutations stay disabled until the helper is installed.

“Start Server At Login” records `kern.bootsessionuuid` in `~/.botfleet/startup-session`, then writes either `startup-enabled.marker` or `startup-disabled.marker` and removes the opposite marker.  “Start Server” enables and bootstraps `app.botfleet.server` if needed, removes `~/.botfleet/stopped.marker`, and kickstarts without terminating a running instance; a failed kickstart restores a previous stopped marker.  Both controls require the installed `~/apps/botfleet-server-start.sh` wrapper to contain `BF_CONTROL_STARTUP_POLICY_V1`; unsupported installations show an update message.  The wrapper allows recovery during the current boot, honors disabled login startup on the next boot, and treats explicit enabled startup as authority to clear a stopped marker from an older boot.

“Launch Control At Login” uses `SMAppService.mainApp`.  Hiding the icon leaves the process and server running; opening `BotFleet Control.app` again restores the icon.  Quitting Control never changes the server.  Closing the Electron BotFleet window releases Electron; the server's separate “Keep Server Running After Quitting BotFleet” setting determines whether it continues.

## Managed Services

The “Fleet Services (12)” submenu lists every long-lived process BotFleet starts on this Mac, and what the Control app can see of each one right now.  The BotFleet MCP Server is first, then the BotFleet Server, the BotFleet Companion, and the pm2 applications the ecosystem file defines.  Each row opens into the actions that make sense for the state that was seen: Start, Stop and Restart.

The state of a pm2 application is what `pm2 jlist` reports, and it is changed with `pm2 start`, `pm2 stop` and `pm2 restart`.  The ecosystem file is the way back when pm2 no longer remembers an application, for a start and for a restart alike.  The state of a launchd agent is what `launchctl` reports, and it is changed with the same launchctl calls the startup policy already uses.  A launchd agent the owner stops is disabled in launchd's own record and booted out, so it stays stopped across logins and restarts until the owner starts it again, which enables it.  Whether the stop took is read from `launchctl print`, never from the bootout's exit status, which is nonzero while a teardown is still in progress and when the job was already gone; an agent that is still loaded afterwards is put back to enabled and the refusal says so.  While an agent is disabled, bootstrapping it by hand (the recipe in its plist header) fails until it is enabled again with `launchctl enable gui/$(id -u)/<label>` or Start in Control.  Restarting the BotFleet Server clears the deliberate-stop marker first, because the installed wrapper stays down while that marker exists.  The BotFleet MCP Server keeps its own health endpoint at `127.0.0.1:8794/health` as the only authority on whether it is running.

The BotFleet Server is stopped by asking the server itself, not by booting its LaunchAgent out: launchd does not always own the process, because the installed wrapper exits when the harness is already healthy and the desktop app forks its own harness when nothing answers on the port, so a bootout can leave a server that is still serving.  The server refuses the stop while work is in flight, exactly as “Stop Server And Local VMs…” does.  When the server is older than Control and has no stop route, the row's Stop takes the same marker-and-bootout path as that item, with no in-flight-work check and with the Local VMs left running.

The wanted state of a service is derived and never stored.  The BotFleet MCP Server is wanted exactly while the BotFleet Server is running.  Every other service is wanted on its own: it is wanted unless something explicitly says otherwise, and the only thing that says otherwise is the service itself, so a service that was stopped on purpose stays stopped and one that failed is brought back up.  A stop the owner asked for in this submenu is remembered until the owner starts that service again, so the reconciler does not take it back; the memory lives in `~/.botfleet/control-owner-stops.json`, written atomically with mode 0600, so it outlives a relaunch of Control, a login and a restart, and a record that could not be written is reported on its own menu line until a later write succeeds; the file stays in `~/.botfleet` like `control-hosts.json` and `control-vm-plugins.json`, because it is Control's own, where the markers the server and the wrapper also read follow the server's `OMB_DATA_DIR`.  The list is reconciled in the background so a slow `pm2` call never holds the menu open.

Every look at a pm2 application spawns a node client, so a change is waited for with a few wide looks rather than many narrow ones: eight looks two and a half seconds apart, which is the same twenty-second window as before with a quarter of the processes.

## Monitored Processes & Ports

The “Monitored Processes & Ports” submenu reads the fleet’s own processes and the ports they hold every time the menu opens, using `ps` and `lsof`.  It lists each fleet process with its name, PID and port, and each port with the process holding it.  A process belongs to the fleet when it is one of the fleet helpers, the BotFleet server, this app, or a development server running out of a BotFleet checkout; a checkout running its own tests is not part of the fleet and is never offered for stopping.

A helper is an orphan when nothing is driving it any more: neither the BotFleet server nor a process manager is anywhere in its parent chain, so it was left behind and is only holding a port.  A development server out of a BotFleet checkout is always an orphan, because it is never part of the running fleet.  “Terminate … (PID …)” stops one process, “Free Port …” stops whatever holds one port, and “Kill Orphan BotFleet Processes” stops every orphan at once.  Each one says what it will stop before it does, and the app refuses to stop PID 1 or itself.

## Remote VM Provider Plugin

The app does not know how a remote machine is hosted, so the owner picks a provider and the app asks that provider.  `VMProviderPlugin` is the whole contract: the machine’s state, and three actions — start, stop and shut down.  Three providers ship with it.  `BotFleetServerVMProvider` asks the BotFleet server’s own control API about the virtual machine it runs on.  `HetznerCloudVMProvider` asks the Hetzner Cloud API about a server id, with the owner’s own token.  `CustomScriptVMProvider` runs the owner’s script with one argument — `status`, `start`, `stop` or `shutdown` — where a status call prints `running` or `off`.  A new provider is a new type that implements the protocol; nothing else in the app has to change.

The configuration lives in `~/.botfleet/control-vm-plugins.json`, written atomically with mode 0600 because it holds API tokens.  “Configure Remote VM Provider…” asks for the server, the provider, the machine’s id, the token, and the script, and “Remove Remote VM Provider” forgets the answer without touching the machine.
