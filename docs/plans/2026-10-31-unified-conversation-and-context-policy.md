# One Conversation Per Bot: Unified History, Browsing During Work, and a Configurable Context Policy

Status: draft for review, Fri, Oct 31, 2026.  Owner issue BF-2444 (plan only; the implementation owner is Jay's call).  Refs BF-2544, BF-2559, BF-2501, BF-2510, BF-2511, BF-2514, BF-2515, BF-2536.  Written from the tree at `5f43cb24` (the code facts are identical to `origin/main` `4112e26e`; that head adds only orb setup files), read-only — nothing built, run or migrated.  The prior fleet-matrix documentation (PR #1033, `docs/audits/2026-10-09-fleet-matrix-ux-panel/`) already framed the core finding this plan formalizes: **browsing must be separated from execution targeting**.

This plan says how BotFleet moves from "a bot is one active task with frozen tabs" to Jay's approved direction (BF-2444, Oct 25): one persistent conversation per main bot with scoped background execution contexts, a reversible migration that unifies each bot's existing threads into one history, a configurable context budget with real compaction methods (not just cutoff), and — available immediately, before any migration — independent browsing of a bot's other threads while that bot works.  It authorizes no live migration, no data deletion, no settings change and no cutover.

## Rulings This Plan Follows

- **BF-2444 (Jay, Oct 25, selected product direction).**  One persistent user-facing conversation per main bot, with task execution contexts distinct from the visible conversation; the main bot stays available to the user while scoped background agents perform tasks; the parent owns delegation, progress, results and cancellation; delegation does not expand credentials or permissions; task/result routing stays preserved and task activity is clearly distinguished in the conversation.  Existing per-bot history is unified by a **reversible** migration that merges each bot's threads into one conversation history, preserving original IDs, timestamps, attachments, task/source labels, provenance and permissions; nothing is destructively deleted; different bots, users and private audiences are never combined.  Context is **configurable independent of retained history**: a budget (e.g. last 5 prompts, last 1–2 prompts, or a token amount), with clearly labeled user prompts versus complete prompt/reply exchanges, a choice between cutoff and compaction, **multiple compaction methods** (not a binary choice), and a manual "Compact now" action applied at safe in-flight task boundaries.  Retained history is never silently deleted because the context budget is small.  A dedicated alert bot with a minimal budget is one supported configuration, not the only shape.
- **BF-2444 interim requirement (Jay, Oct 25).**  Until threads are unified — and after unification for full history — the user must be able to open, read, scroll, search and copy another retained thread **while the same bot continues work**.  Viewing must never switch tasks, cancel or restart work, alter model context, change default automation destinations, or redirect messages.  Reading positions and drafts are preserved; streaming and reconnects must not force navigation away from the history being inspected.
- **BF-2444 source complaint (Echo, via JET; Sentinel messages Oct 2026).**  "When one BotFleet thread is active, Jay cannot view that bot's other threads."  This is a current-behavior defect independent of the redesign.
- **BF-2544 / BF-2559 (Jay, Oct 25/29).**  Server-first hybrid operation is optional and configurable; the native Mac UI stays; one authoritative job queue/state/ownership record; the Linux server and the standalone headless path survive the rewrite (BF-2514/2515 reconciliation gates).  This plan must therefore work in **both** the Node harness (today's writer) and the native Mac app (ios/Sources), and must not assume a future in-process-only world.
- **BF-2444 scope guard.**  This issue approves product direction and planning only — no live migration, no data deletion, no bot reconfiguration, no deployment.  Route implementation through the existing P-BF-6 lanes; no competing writer.
- **PR #1033 / fleet-matrix findings (`docs/audits/2026-10-09-fleet-matrix-ux-panel/`).**  R8 (Codex, Q6 "Separate looking from operating"): "Browsing should preserve execution destination."  R10 (Instinct): "room for context, bot for execution ownership, thread for conversation history."  R7 (AG): a single busy flag per bot falsely marks every home "Working."  Ranked rec #1: "Make thread identity explicit end to end: independent viewing, exact card destinations, explicit execution targeting."

## What Exists Today

- **A bot already has multiple tasks, but only one is reachable while busy.**  `BotRecord` holds the active task's `threadId` ("everything that runs a turn reads this", `server/store.ts:627-637`) plus `tasks?: TaskRecord[]` ("every task this bot has, newest first").  `TaskRecord` is one conversation with its own transcript, its own `resumeCursors` per provider instance, its own usage ledger, and its own pinned `cwd` (`server/store.ts:358-433`) — the "one endless thread contaminated every job" comment is still in the record's documentation, which is exactly the history-unification problem.
- **The default conversation mode is "simple" = one conversation per bot.**  `shared/conversation-mode.ts:29` (`DEFAULT_CONVERSATION_MODE: "simple"`), and `allowsMultipleBotThreads(mode)` returns `true` only for `"projects"` (`shared/conversation-mode.ts:43-45`).  In simple mode the web sidebar hides task nesting entirely (`src/components/Sidebar.tsx` gates on `allowsMultipleBotThreads`, per `src/components/ChatView.tsx`/`TaskPicker` usage), so most of Jay's bots are single-thread by policy, not by capability.
- **Switching tasks is the only way to address a thread, and it is busy-gated.**  The server refuses `POST /api/bots/:id/tasks/:threadId` with 409 "this bot is working — stop it before switching tasks" while `bot.busy` (`server/index.ts:16575-16585`, comment kept verbatim above the guard); task creation and merge are refused on the same flag (`server/index.ts:16556`, `:16592`); the internal `activateTask` hook refuses while busy.  The web client pre-emptively disables the same paths: App-deeplink switching is skipped when busy (`src/App.tsx:160-162` — `if (threadId && threadId !== b?.threadId && !b?.busy)`), thread-tab buttons for non-active tasks are `disabled={busy && !active}` and dimmed (`src/components/ThreadTabs.tsx:118-119, 179`), "New thread" is `disabled={busy}` with the tooltip "Let this turn finish first" (`src/components/ThreadTabs.tsx:209-211`), the task picker matches (`src/components/TaskPicker.tsx:156-157, 290, 308`), and new-task requests early-return on `bot.busy` (`src/state/store.tsx:2078-2082`).  This is the reported defect, and the guards are deliberate: switching *is* retargeting in today's model, so blocking it is the only way the current design can protect an in-flight turn.
- **The send route hard-couples messages to the active task.**  `POST /api/bots/:id/messages` resolves `expectedThreadId = body.threadId ?? bot.threadId` and 409s "the message targets a thread that is not the bot's active task — the message targets a thread that has moved on" when they disagree (`server/index.ts:16013-16042`).  A pinned-but-not-active thread therefore cannot receive input without first becoming active, which while busy is impossible (guard above).
- **The web store keeps one transcript per bot.**  The `messageAdded` reducer finds the bot by `b.threadId === action.threadId` and drops frames for any other thread of that bot (`src/state/store.tsx:1712-1716`); hydration embeds only the active transcript (`publicBot` → `wireBot` assembles `bot.threadId`'s messages, `server/index.ts` `publicBot`/`wireBot` path).  The client-side "pin" (`viewedThreadId`, `src/lib/task-app-thread.ts`) is display-only shadowing (`src/components/ChatView.tsx:1144-1153`) and the code itself admits a pinned non-active thread would "render a transcript the store never loaded" (`src/App.tsx:359-361`).  So even client-side, "view another thread" has no data path in simple mode.
- **The server fan-out already carries every thread.**  `broadcast()` sends each frame to every connected client with the frame's `threadId` on it (`server/index.ts` broadcast paths; frame kinds `message`, `messages`, `message.patch`, `thread`, `thread.deleted` — `server/store.ts:608-613`).  The iOS fold already keeps transcripts **per thread** and appends frames for any thread id (`ios/Sources/CompanionCore/Store.swift:24`, `:24-43` message/streaming application).  Reading thread B while A streams is a client-store problem, not a wire problem.
- **The native Mac app is already view-only during work — and it is the good path.**  `MacSession` computes `activeThreadId = selectedThreadId ?? room.threadId` (`ios/MacApp/MacSession.swift:269` region) with no server mutation on selection; `MacApp` never calls `switchTask`.  The iPhone app is the opposite: `ChatListView.openTask` awaits `session.switchTask(...)` (`ios/App/ChatListView.swift:715`) and `ThreadTabBar`-equivalents disable other-task tabs while busy (mirroring the web gates).  The interim fix is largely "make iOS and web behave like the Mac already does."
- **Automation targets the active thread, not a pinned thread.**  Routines, webhooks and resource triggers that do not name a thread resolve to the bot's active thread (`server/index.ts:16013+` default and the routine default-target path; PR #1033 R8 flagged the same coupling for default routine targeting).  This is the coupling the unified model must break: a conversation's *identity* must not depend on which task happens to be active.
- **Context budgeting already exists in two narrow forms.**  ACP engines replay bounded history: `maxHistoryTurns` caps replayed turns ("older turns are dropped and summarized even when the byte budget would fit them", `server/store.ts:693-696`) and `historySummaryModel` turns the dropped tail into a model-written summary that is cached and rolled forward (`server/store.ts:697-700`); the byte-level budget is applied in the ACP prompt builder (`server/turn-context.ts` — `MAX_REPLAY_BYTES`), with `src/lib/transcript-window.ts` doing the display-side folding.  `server/model-context-windows.ts` maps model ids to context windows for warnings.  HTTP tool-loop engines have no equivalent user-facing knob today.  There is no manual compaction action, no per-bot budget setting, and no visible effective-policy surface.
- **Merging exists.**  `store.mergeBotTasks` re-points automation keys and moves the transcript rather than copying it (`server/store.ts` merge path; `PATCH …/tasks/:threadId` with `mergeInto`, `server/index.ts:16592+`).  The migration can reuse this primitive; the migration's job is to make it reversible and provenance-labeled at scale.

## The Target Model

One persistent conversation per main bot, with execution contexts behind it.  Concretely:

- **The bot's conversation is the identity.**  `BotRecord` gains a stable `conversationId` (minted once per bot, never reused across bots).  The active task's thread keeps working during the migration; after it, `bot.threadId` resolves through the conversation rather than being the only handle.  Sessions, resume cursors and pinned cwd stay attached to **execution contexts** (today's `TaskRecord`), never to the visible conversation.
- **Tasks become execution contexts, not competing front doors.**  A task keeps exactly what it has today — its own transcript, cursors, cwd, usage.  What changes is addressing: the parent conversation can spawn a background context, route delegated work to it, watch progress and cancel it, while the user keeps talking to the parent.  The parent's transcript shows task activity as attributed, labeled entries (tool/source labels already exist on messages; delegation messages already exist as a distinct kind — `shared/delegation-message.ts`).
- **Viewing is always passive.**  Opening any thread — the parent conversation, a background context, or a pre-migration retained thread — reads and renders; it never dispatches, never retargets, never redirects a future message.  Sending into a non-active context is an **explicit** act (a "send here" affordance on the open context), and the busy/concurrency safeguards move with it: the server keeps refusing to *retarget the active turn* while busy, but stops refusing to *read*, and gains a per-context send that queues or runs in its own context without disturbing the parent's in-flight turn.
- **Everything the plan adds works identically under the Node harness and the native rewrite.**  All new state lives in the same store layer both clients read (`server/store.ts` shapes, mirrored in `ios/Sources/CompanionCore/Store.swift`), so the P-BF-6 port inventory rows stay one-to-one.

## Slice 0 — Interim: Independent Browsing During Work (landable now, no migration)

This is the reported defect and the issue's own interim requirement.  It needs no new product concepts, only the decoupling the fleet-matrix panel recommended:

1. **Serve transcripts for any of a bot's threads.**  `wireBot`/`publicBot` gains an optional `includeThreads` or a per-thread transcript endpoint (`GET /api/bots/:id/threads/:threadId/messages`) reading the same `messagesFor(threadId)` path the store already exposes (`server/store.ts` messages API).  Reused for the unified history later.
2. **Web: per-thread client transcripts + busy-free viewing.**  The web store keeps a `Map<threadId, Message[]>` for threads the user has opened (mirroring `ios/Sources/CompanionCore/Store.swift:24`), applies SSE `message`/`message.patch` frames by `threadId` regardless of which task is active, and keeps the reading position and composer draft per opened thread.  The busy gates change from "cannot open" to "can open, cannot *become* the execution target": `ThreadTabs`, `TaskPicker` and App-deeplinks allow selecting any task while busy (`src/App.tsx:160-162`, `src/components/ThreadTabs.tsx:118`, `src/components/TaskPicker.tsx:118`), but the *activate* affordance stays disabled while busy with its existing tooltip.
3. **Server: keep the 409 for switching, never for reading.**  `POST /api/bots/:id/tasks/:threadId` keeps its busy guard (retargeting an in-flight provider session stays unsafe — the comment above the guard is correct and this plan does not weaken it).  Read routes never consult `busy`.
4. **iOS: stop switching on open.**  `ChatListView.openTask` (`ios/App/ChatListView.swift:715`) views instead of switching while the bot is busy, mirroring the Mac's selection-only behavior; the explicit switch affordance keeps the existing guard.
5. **Send-to-viewed-thread.**  The composer on a pinned non-active thread posts to a new explicit route (`POST /api/bots/:id/threads/:threadId/messages`) that either queues the message for when that context can run, or — if that thread is backed by its own idle execution context — dispatches there.  It never re-points `bot.threadId` while busy, so the parent's in-flight turn and default automation targeting are untouched.  The active thread's send path stays byte-identical.

Acceptance (from the issue): while bot A works, opening and scrolling its retained thread B shows B's history, B keeps receiving frames if anything writes to it, A's output/routing is unchanged, and rapid navigation, reconnect and two-client tests preserve the contract.  Browsing must also survive the native rewrite (Mac already complies; iOS and web adopt Slice 0 semantics).

## Slice 1 — Unified Conversation History and the Reversible Migration

One merged conversation history per bot, preserving everything.

- **Data model.**  Each bot gets `conversation: { id, entries }` where an entry references a message by its original `(threadId, messageId)` pair plus `{ sourceTask, provenance, originalTimestamp }`.  Original thread files (`messages-<threadId>.json`) are **never** rewritten or deleted — the conversation is a stored ordered projection over them, so rollback is dropping the projection.  This satisfies "preserving original IDs, timestamps, attachments, task/source labels, provenance and permissions" without a risky transcript rewrite, and it reuses the existing per-thread files the store already treats as the durable record (`server/store.ts:1-5`).
- **Merge primitive.**  `store.mergeBotTasks` already moves a transcript into a task without copying; the migration extends the same move semantics across a bot's whole `tasks[]` into the conversation projection, tagging each entry with its source task id, title and creation order.  Bots' histories are never combined with other bots, users or private audiences: the projection is per-bot by construction, and room transcripts (`GroupRecord`) are out of scope.
- **Ordering and identity.**  Entries sort by original timestamp, then by original per-thread order, with a stable tiebreak on message id.  The `conversationId` is the link identity; retained thread ids remain valid addresses forever (old links, deep links and API callers keep working).
- **Verification and rollback.**  A pre-cutover dry run computes, per bot: entry count vs summed per-thread message counts, attachment presence, and provenance-label completeness; any mismatch aborts that bot's cutover.  Rollback is: stop using the projection (clients fall back to per-thread reads), which is possible at any time because originals are untouched.  The migration runs per bot, is resumable, and is behind a flag.
- **Cutover order.**  Web → iOS → Mac native, in that order, because the Mac's view-only model already complies and the web's store is the most invasive change.  The Electron app is decommission-bound (BF-2485 lane) and only needs read compatibility.

## Slice 2 — Configurable Context, Independent of Retained History

- **Per-bot settings (bot profile surface, `shared/bot-profile.ts` and the bot settings UI):**
  - `contextBudget: { kind: "prompts", value: n } | { kind: "tokens", value: n } | { kind: "off" }`, default `off` (today's behavior).
  - `contextPolicy: "cutoff" | "summarize" | "hybrid"`, where `cutoff` drops older turns, `summarize` is today's `historySummaryModel` rolling summary generalized to all engines, and `hybrid` keeps the last complete exchanges verbatim and summarizes the rest.
  - A "prompts" count means **complete prompt/reply exchanges** — the issue's labeling requirement: the settings UI shows "last N exchanges" and the effective prompt shows the boundary, never a half exchange or a split tool-call/result pair.
- **Manual "Compact now".**  A conversation action that compacts the *retained-but-out-of-budget* history into the summary **at a safe task boundary**: if the bot is mid-turn, the compaction is staged and applied when the turn settles (the same settle point the replay machinery already uses for cursor/summary roll-forward).  The result is shown: method, what was compacted, what stays verbatim, and when it took effect.  Compaction never mutates the retained conversation projection — it produces a summary entry plus a "verified through" watermark, so it is itself reversible by clearing the watermark.
- **Overflow and failure behavior.**  If compaction fails (model error, budget impossible), the turn proceeds with `cutoff` semantics and the failure is surfaced in the transcript — never a silent history loss.  If the effective prompt still exceeds the model window (`server/model-context-windows.ts`), the oldest exchange is dropped with a visible "dropped to fit" note.
- **Minimal-context bots.**  The alert-bot configuration (`contextBudget = last 1 exchange`, `cutoff`) is just settings; nothing special-cased.  Delegated background contexts receive only the task-relevant slice of context the parent passes at spawn time (`server/context-injection.ts` already exists as the seam for injected context) plus their tools — never the parent's full history.
- **Effective-policy visibility.**  The conversation view shows the active budget/policy and, per turn, whether the prompt used the full window, a summary, or a cut — derived from the same telemetry the ACP path already reports.

## Slice 3 — Background Delegation Alignment

The parent owns delegation: spawn, progress, results, cancellation.  This slice formalizes what the app already half-has (delegation messages, task records, job cards):

- Spawn a background execution context from the parent conversation with an explicit context slice and tool grant; the grant cannot exceed the parent's own permissions (`server/tool-policy.ts` boundary).
- Parent transcript renders task lifecycle as attributed entries (started / progress / result / cancelled) with a jump link to the context's own transcript.
- Cancellation is parent-owned and reaches the context's running turn through the existing interrupt path, which today keys on the running thread (`inflightThreadId`, `server/store.ts:3043` region) — unchanged mechanics, parent-routed UX.
- Concurrency: the bot-level busy flag becomes per-context; the parent stays responsive while a background context runs (the R7 finding's fix).  The aggregate admission rules (one turn per context; job caps) are unchanged.

## Integration Boundaries and the Native Rewrite

- Clients touched: web (`src/`), iOS (`ios/App/`), Mac native (`ios/MacApp/`), and the Node server (`server/`).  The Electron app needs read compatibility only (retiring lane BF-2485).  The fleet-matrix panel's instruction to inventory shared APIs is satisfied by Slice 0's route additions, which are additive and versionless.
- The Node harness and the standalone headless server path are preserved (BF-2514/2515 reconciliation): nothing here removes `server/` functionality; the conversation projection is additive state in the same store.
- Server-first (BF-2559) is unaffected: the conversation projection lives on whichever store is authoritative, exactly like today's transcripts.

## Open Questions for Jay

1. **Default budget for existing bots after migration:** leave every existing bot at `off` (no behavior change), or seed a sensible default (e.g. last 5 exchanges, hybrid)?  The issue's examples suggest a default exists; the safe reading of "configurable" is `off` until the user chooses.
2. **Send-to-inactive-context default:** queue-until-free (my recommendation: yes, queue with a visible pending state) or dispatch-in-parallel immediately?
3. **Should the unified conversation show pre-migration threads' titles inline as collapsible sections, or as one flat merged history?**  Provenance labels support either; the flat merge is simpler and matches "merge existing threads."
4. **Does the iOS app need Slice 0 before the unified-conversation work, or can it land together?**  The Mac needs nothing; web and iOS both need the per-thread store either way.

## What This Plan Does Not Do

No live migration, no cutover, no data deletion, no settings change, no bot reconfiguration, no deployment, no credential or permission change.  It does not touch the Electron app's runtime behavior, does not weaken the existing busy-guard that protects in-flight provider sessions (that guard stays for *switching*; only *reading* is freed), and does not create a second authoritative controller — the store layer remains the single writer in every mode.
