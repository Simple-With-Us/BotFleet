# iOS Companion Topology Under Server-Based Placement

Status: source-verified topology and contract-prep record (`Refs BF-2652`), updated on branch `ag/bf-2652-companion-sync-contracts` over `origin/main` commit `55222043f` (building on the `804ecc9be1f66142752729ed3cb25f094966af6d` baseline).  This document is not live verification: no iPhone pairing, hosted HTTPS probe, Tailscale failover, foreground SSE cursor replay, or physical APNs delivery was executed against any Mac, server, or device.

## Outcome And Boundary

`BF-2652` asks how the iOS companion stays consistent when BotFleet runs in a server-based placement mode without inventing an unnecessary sync protocol or authorizing premature server exposure.  This record distinguishes what the codebase currently ships, which endpoint, pairing, SSE, and push contract gaps were closed in source and unit fixtures, where server-owned state still diverges from Mac-local companion state, and which items require Jay's approval or a physical iPhone before live `BF-2652` acceptance runs proceed.

## Placement Modes And State Ownership

`shared/placement.ts` defines `PlacementMode = "localOnly" | "serverFirst" | "macFirst"`.  Per `docs/plans/2026-10-29-native-server-mode.md`, authoritative job-state ownership and companion reachability differ across the three modes as follows:

| Mode | Controller Host | Worker Host | Authoritative Job Records | Companion Impact Under Option C (Phone Pairs With Mac) |
| --- | --- | --- | --- | --- |
| `localOnly` | Mac (`127.0.0.1:8799` / native runtime) | Mac (same host; no separate worker) | Mac only (`docs/ios-companion.md`) | Local state matches Mac companion responses 1:1. |
| `macFirst` | Mac | Linux server (optional overflow / remote worker) | Mac owns controller records; Linux worker runs leased jobs and spools reports | Controller records reside on the Mac, though worker output and completions depend on the lease/heartbeat/spool link staying healthy. |
| `serverFirst` | Linux server (`deploy/linux-server/`) | Mac (when `allowOverflowToThisMac` is enabled or job requires `macos` / pin) | Linux server owns controller records; Mac worker holds local lease records only while running a leased job | **Gap:** Mac companion state currently reads local Mac state only; unbridged `NativeCompanionServer` or sleeping-Mac setups do not reflect server-owned jobs, approvals, or completions. |

## Shipped Path Versus Option C Ruled Architecture

Three completed Linear issues establish the baseline contract: `BF-2510` (*Decide the iOS Companion Endpoint After the Node Harness*, state `Done`, completed `2026-10-29T20:36:13Z`), `BF-2511` (*iOS Companion API After Node: Build the Chosen Endpoint*, state `Done`, completed `2026-11-13T18:42:45Z`), and `BF-2591` (*Native companion server speaks the iOS client's pairing contract*, state `Done`, completed `2026-10-30T22:18:38Z`).

### What Currently Ships On Main

- **Node companion sidecar (`docs/ios-companion.md`, `companion/src/index.ts`, `companion/src/proxy.ts`, `companion/src/apns.ts`):** Port `8810` proxies the local harness (`8799`), serves SSE (`GET /api/events`), enforces pairing/device allowlists, advertises LAN/Tailscale endpoints, and watches local harness notifications (`watchHarnessNotifications`) for APNs alerts.  `docs/ios-companion.md` records that hosted HTTPS is **not available in current builds**.
- **Linux server deployment excludes `companion/` (`deploy/linux-server/retained-source.json`, `deploy/linux-server/botfleet-server.service.in`, `deploy/linux-server/owner-gate.mjs`):** The server deploy manifest retains `server/placement-*.ts`, `shared/placement*.ts`, `server/companion-writes.ts`, and `deploy/linux-server/owner-gate.mjs`.  The retained server harness serves port `8799` (`botfleet-server.service.in`), and `owner-gate.mjs` provides the owner gate on port `8798`.  The deployment retains zero `companion/` sidecar files and ships no companion `:8810` listener in `deploy/linux-server/`.
- **Native `NativeCompanionServer` & `CompanionListenerController` (`ios/Sources/CompanionCore/NativeMacCompanionRuntime.swift`, `ios/Sources/CompanionCore/NativeCompanionServer.swift`, `ios/Sources/CompanionCore/CompanionListenerController.swift`):** `BF-2510` and Option C (`docs/plans/2026-10-29-botfleet-control-after-node.md`) ruled that the native Mac app hosts the companion API.  On `main`, `CompanionListenerController` defaults to `.off`, and `NativeMacCompanionRuntime.makeServer()` initializes `NativeCompanionServer` without placement settings or a controller client.
- **Pre-login native host remains design-only (`docs/plans/2026-10-30-optional-prelogin-host.md`):** No headless pre-login native companion service executable or LaunchDaemon ships today.  `ios/MacApp/MacSession.swift` only runs inside an interactive GUI login session.

## Verified Topology Gaps For `serverFirst`

Inspection identifies four concrete topology gaps separating current `main` from verified `serverFirst` iOS companion sync:

1. **Controller-to-companion state gap:** In `serverFirst`, the Linux controller owns job records, queues, and approval waits.  Neither `companion/` on Mac nor `NativeCompanionServer` currently proxies or merges controller-owned fleet, thread, wait, or SSE streams from a remote Linux controller.
2. **Server sleep / Mac availability gap:** Because `deploy/linux-server/` ships no companion listener and Mac `MacSession.swift` is per-user post-login, pairing the phone exclusively to the Mac means a sleeping or logged-out Mac cuts off phone access to server-running jobs unless either a server-side companion route exists or the phone pairs directly over an approved route.
3. **APNs delivery source gap:** `companion/src/apns.ts` (`watchHarnessNotifications`) monitors a single local harness, and `NativeCompanionServer` tracks push registrations locally.  When the Linux controller completes a job or hits an approval wait while the Mac listener is asleep, nothing on the Linux server currently dispatches APNs notifications to phone tokens registered only on the Mac.
4. **Published HTTPS & route policy gap:** `ios/Sources/CompanionCore/Client.swift` already models `endpoints`, `allowedRouteKinds`, and `allowedLocalRouteURLs` for hosted HTTPS alongside LAN/Tailscale.  However, hosted HTTPS is not built yet, and `NativeCompanionServer` by default echoes whatever endpoint advertisement the app injects.

## Real-iPhone Verification Checklist

The following end-to-end checks cannot be proven in headless unit tests or iOS Simulator alone and require an actual iPhone paired to a Mac (and configured `serverFirst` deployment):

1. **Real network discovery & pairing (Wi-Fi / Tailscale / HTTPS):** Pair the physical iPhone over local Wi-Fi (`_botfleet._tcp` Bonjour plus iOS Local Network permission), Tailscale MagicDNS (`*.ts.net`), and/or hosted HTTPS using both a scanned QR invite and manual 6-digit code.  Confirm Keychain token persistence survives iOS app force-quit, Mac app restart, and reboot.
2. **Live foreground SSE sync & background wake cursor replay:** Verify live SSE `hello` cursor negotiation, message streaming, and wait/approval updates while foregrounded, then background the iPhone, generate server events, wake the app, and confirm `Last-Event-ID` / `?since=` cursor replay fills the gap without duplicate alert banners (`PushDeliveryLedger`).
3. **Device revocation over live socket:** Revoke the paired iPhone from the Mac side while `/api/events` is open and confirm the active SSE connection terminates immediately and the phone transitions cleanly to its `401` re-pair prompt.
4. **Physical APNs background push & Live Activity `push-to-start`:** Trigger approval/completion notifications while the iPhone app is backgrounded or terminated to verify real Apple APNs delivery (simulators cannot receive production APNs), time-sensitive notification actions (`Approve` / `Deny`), and end-to-end Live Activity `push-to-start` token registration and delivery.
