# Native Server Mode: Optional Linux Host, One Owner Per Job, Honest Headroom

Status: draft for review, Thu, Oct 29, 2026.  Owner issue BF-2559 (plan only; the implementation owner is Jay's call).  Refs BF-2544, BF-2514, BF-2515, BF-2510, BF-2528, BF-2531, BF-2513.  Written from the tree at main 7c49bc95 and from read-only facts gathered on fleet-hetzner-nbg1 at 2:21 PM and again that evening.  Three independent designs (user-first, ownership-first, incremental-landing) and two judges fed this draft; the judges preferred the incremental-landing slicing with the ownership-first fence and the user-first copy rules grafted in, which is what follows.

This plan says how the native Mac app gains an optional Linux server as a second host without ever having two controllers, how a job gets exactly one owner in every mode, what Settings shows for per-host headroom and what it may never claim, and which evidence closes BF-2559 so that BF-2514 and BF-2515 can read it.  It proposes no numeric budget: the owner said measured inventory comes first, and until it exists the only protections are the swap and free-disk gates the harness already has.

## The Modes

Three modes, shown as one radio group under Settings › Servers titled "Where Bots Run".  A mode fixes who the controller is and which hosts may run work; nothing else about ownership is decided at run time.

- **This Mac Only** (`localOnly`), the default on every install.  Controller and worker are this Mac.  No server is contacted, no pairing, no account, no vault bootstrap.  The word "server" appears nowhere outside Settings › Servers until the person adds one.  This is the BF-2544 acceptance: a fresh install completes normal jobs with no server configured.  Its caps keep today's ruling, refused past a cap and never queued, unless Jay answers open question 8 the other way.
- **Server First** (`serverFirst`).  Controller: the chosen server.  Workers: the server and this Mac.  The server keeps every placeable job's record and keeps dispatching while the Mac sleeps, which is why Jay wants it.  This Mac runs Mac-only work, work pinned to it, and, when "Allow Overflow To This Mac" is on (the default inside this mode), overflow when the server is at its budget.  With the toggle off, the Mac runs only Mac-only and pinned work, which is the nearest honest equivalent of the Electron remote mode.  In this mode the Mac never admits a placeable job on its own.
- **This Mac First** (`macFirst`).  Controller: this Mac.  Workers: this Mac and the server.  Eligible jobs go to the server only when this Mac's RAM or disk gate refuses them, which is the literal "offload some of the Mac".  When the Mac sleeps nothing is dispatched; that is the honest cost of keeping the record on the Mac.  In this mode the server never admits a job on its own.

Enablement.  The two server rows are always visible and disabled until a saved server has passed the handshake (identity, host id, version, auth, capabilities, and the placement routes answering).  With no saved server the caption reads "Add a server to use this mode."  With a server never reached: "Test <name> below to use this mode."  With a server that answers but has no placement routes: "<name> is running version <v>, which has no placement routes.  Update the server to use this mode."  The same rule holds on the API, so no script can set a mode the UI refuses.  The rows are not drawn at all until the slice that makes them do something has landed; a mode that does nothing is never offered.  Remove Server is refused while that server is the controller or holds a lease, with the reason.

Pinning.  Independent of the mode, every bot and every job keeps "Run on: Automatic / This Mac / <server>".  A pin to a host that cannot run the job's capabilities is refused at save time with the reason ("Desktop control only runs on this Mac").  BF-2544 asks for explicit placement first, and pins are that.

Placeable work in version one: background jobs (`job_start`, `server/jobs/registry.ts`) and unattended routine and webhook runs.  Interactive turns are not placed in version one: they run on the host the person is talking to, so a bot holding the This Mac grant keeps working in every mode, and dispatching turns to a worker is a follow-up issue (open question 11).  A running job never moves between hosts; transfer happens only at a job boundary, which here means a job finishes where it is and the next one is placed fresh.

Transitions.  The mode record is `{ mode, controllerId, epoch, serverId, allowOverflowToThisMac }`, persisted on both hosts (the Mac in `DatabaseService`, the server beside `jobs.json` with `writeFileAtomic`).

1. `localOnly` to `macFirst`: needs a verified server; the Mac stays controller, the epoch does not change, the server is told it is a worker for controller `<macId>` at epoch N.  No job moves; allowed with work in flight because ownership does not change.
2. `macFirst` to `localOnly`: needs no server lease active, or the person stops those jobs first ("Finish or stop 3 jobs running on the server first").  The server's worker registration is cleared.
3. `localOnly` or `macFirst` to `serverFirst`: needs a verified server and no Mac-owned active job (the same fence `/api/system/control/stop` applies).  In order: the Mac writes "handoff pending"; the server writes `{ controller: server, epoch: N+1 }` and acknowledges; the Mac writes the same and registers as a worker.  On a lost acknowledgement the Mac asks the server for its `{ controllerId, epoch }` and converges to it.  Nothing is re-enqueued, because This Mac Only holds no queue.
4. `serverFirst` to `macFirst` or `localOnly`, clean: the server is reachable and no server-owned job is active on either worker, or the person stops them.  The server writes "released at N+1" and refuses new `job_start`; the Mac writes `{ controller: mac, epoch: N+1 }`; the server confirms as a worker or detaches.
5. `serverFirst` to `localOnly`, forced ("Take Over On This Mac…" while the server is unreachable): the one transition that may leave work behind, so it is visible and deliberate.  The dialog lists the server-owned jobs last known running there as "will keep running on the server and be shown as orphaned until it returns"; the Mac writes epoch N+1; any later message from the server at epoch N is refused.  When the server returns it reads the higher epoch, demotes itself, stops admitting, finishes or stops its jobs on request, and reports them; the Mac shows them as "finished on the server after takeover" and never reruns them.
6. Server unreachable and reachable again inside `serverFirst` is a connection state, not a mode change.

Every transition is logged with the epoch before and after, and the Settings status row shows "Server First since 2:14 PM (epoch 7)" so two hosts' logs line up.  The sheet says in one sentence what a switch does: "Running jobs finish where they are.  New jobs follow the new mode."

Migration from Electron: `local` maps to `localOnly`; `remote` maps to `serverFirst` with overflow off and the vault URL as the one saved server; the Infisical bootstrap stays optional and is never required for the Mac-only path.  The credential rule becomes per host ("Keys for work that runs on <server> are set on that server", shown in Settings › Models when a server is saved).

## Ownership And The Split-Brain Fence

Identity.  Each harness writes one stable host id at first boot (`<data dir>/host-id`, mode 0600), and the native app reads this Mac's from its data directory.  `HostId` is "mac:<uuid>" or "server:<uuid>".

One record per job, in the controller's store and nowhere else; a worker holds a lease, never a record it can act on alone.  The record extends today's `JobSnapshot` (`shared/jobs.ts:40-71`, mirrored in `ios/Sources/CompanionCore/Jobs.swift:40-60`) with `controllerHostId`, `host`, `leaseId`, `epoch`, `placedReason` and `queuedReason`, and two new statuses, `queued` and `worker-unreachable`.  Swift already decodes unknown status values to `.unknown` (`Jobs.swift:19-27`), so an older phone never fails on a new state.  `server/job-host.ts:1-8` already states the rule for delegated turns, an assignment written before anything runs and a cut turn rerun once unless it acted outward; placement keeps that rule and adds the host.

Who may admit.  Admission is a function of the stored mode, which only the person writes.  A Mac in Server First forwards `job_start` to the controller and never calls its own registry for an unpinned bot; a Mac in This Mac Only never registers as a worker; a controller refuses a worker whose registration says `localOnly`.  The worker pulls; the controller never dials the Mac.

States: `queued` (admitted, no host yet; `queuedReason` says why it waits), `dispatching(host)` (host and lease written in the same transaction as the state, the dispatch message sent after the write), `running(host)` (the worker acknowledged with its pid), `stopping(host)`, `worker-unreachable(host)` (a missed heartbeat window; the job is not requeued), and the terminal `completed`, `failed`, `killed`, `lost`.  `worker-unreachable` leaves only by the worker's own report or by the visible owner action "Mark Lost", optionally "and start again", which makes a new job id and never reuses the old one.  A claim is a compare-and-set from `queued` to leased; a second claim for the same job is refused.

The fence.  Both hosts persist `{ controllerId, epoch }`.  Every placement message carries the sender's epoch.  A receiver refuses a lower epoch and answers with its own pair, so the sender converges instead of acting.  A worker runs a lease only when the lease's epoch equals its stored epoch.  The epoch increments only on a controller change (transitions 3, 4 and 5), so two controllers can never both hold the current epoch.

No duplicate execution, four rules, each checkable: a dispatch is idempotent on job id (a worker that already holds `leaseId` for job X answers the same acknowledgement and does not spawn; a different `leaseId` for X is refused and reported, because the controller lost state and a person must look); a completion report is idempotent on job id; the controller never requeues a dispatched job on a timer or on heartbeat loss; starting again is always a new job id.  The fixture for all four is a job that writes a nonce file, and the assertion is one file after every fault.

Reconnect.  Each worker heartbeats `{ epoch, running lease ids, admission verdict with reason, capacity sample }` on a short interval, and the controller marks it unreachable after a missed window and back on the next heartbeat.  A restarted worker settles each leased job from its exit file, the registry's `adopt()` pattern (`server/jobs/registry.ts:1172-1223`), and reports every result before accepting a new lease.  A restarted controller leaves `dispatching` and `running` records alone until each worker's first heartbeat.  On reconnect the worker's record wins for a job it still runs.  The Mac worker keeps a small on-disk spool of unsent reports keyed by job id, in the shape of `server/zulip/outgoing-spool.ts`, and drains it on reconnect; a spool of results for jobs the controller owns is a worker's outbox, not a second queue.  If the server's host id in the handshake differs from the saved one, the app stops and says "This is a different server than the one you added".  The reconnect backoff reuses the `MacSession` pattern (`ios/MacApp/MacSession.swift:709-716`).

Server unreachable in Server First (`serverFirst.disconnected`).  Mac-worker jobs continue and their results spool.  A bot's `job_start` is refused with "The server that owns jobs has been unreachable since 2:14 PM.  Run the command with bash if it is short, tell the user, or the user can switch to This Mac Only in Settings", the same refuse-with-reason contract admission already uses (`admission.ts:148-166`).  Routine runs due in that window are recorded as "skipped: server unreachable" rather than run locally.  The menubar and Settings say the same sentence.  Nothing is admitted locally, so no second controller appears by accident; the deliberate way out is transition 5.  A local list of waiting jobs was considered and rejected, because it is a queue outside the authoritative one.

Server unreachable in This Mac First.  The Mac is still the controller: new jobs keep being placed on the Mac when eligible, server-leased jobs go to `worker-unreachable`.

Why no automatic failover.  Promoting the Mac while the server is merely slow is the one design that can produce two controllers at the same epoch for a window, which the owner text names as the thing not to do.  A visible forced takeover with an epoch bump gives the person the same capability with a fence.

Which process is the Mac worker.  Before BF-2514 removes the Mac-local Node harness, the Mac worker is that harness running in a worker role: it forwards `job_start`, claims under its own admission verdict, records the lease before it spawns, spools reports and reconciles on reconnect.  `MacSession` is a client of that harness and shows the merged state; it does not run jobs.  After the cutover the Swift engine (the Phase 4 runners, `ProcessSupervisorActor`, `DatabaseService`) inherits the same lease contract, and that Swift worker needs an issue of its own, because today those runners are libraries nothing in `ios/MacApp` instantiates (BF-2504 and BF-2497 own that).

GB-Oracle's checks, answered: every job has exactly one owner in every mode (the record lives on the controller, the worker holds a lease); SQLite writes stay local to one host (the controller writes its own store, the worker writes its own log, exit file and spool, and no host opens another host's database); the server's update and rollback path is `deploy/linux-server/update.sh` and the retention contract in `docs/native-rewrite-linux-source-retention.md`, with the `linux-server-preservation` evidence key from #1403 gating the decommission.

## The Placement Contract

One authoritative queue, the controller's.  A `job_start` on any host in a server mode becomes a request to the controller; the controller admits, writes the record as `queued`, then places.  The per-thread and per-bot caps stay refusals, because they are about the bot; the per-host cap becomes an eligibility input, so a job no host can take right now is queued with a reason rather than refused.  `job_start` returns `{ ok: true, job: { status: "queued", queuedReason } }` and its notice tells the bot to wait or use bash for something short.  A queued job nobody can take is expired after the controller's queue window, the `queueMs` pattern the delegation runtime already keeps (`server/runtime/types.ts`), with the reason "no host could take it within <n> minutes", not run and not retried.  The queue is first in, first out within a bot, and drains on the registry tick whenever a host's admission flips to yes or a job ends.

Eligibility, in order.  Capability: the job's required set must be a subset of the host's.  Required capabilities come from the pin and from derivation the controller can do without guessing: a cwd that exists only on the Mac (the registry already checks `existsSync(request.cwd)`); a bot holding the This Mac computer grant (`BotComputers.swift:13-18`, `server/local-routing.ts`) is `desktop`; a command whose first word is in a small shared table (`xcodebuild`, `xcrun`, `simctl`, `codesign`, `notarytool`, `osascript`, `open`, and `swift build` under a Mac path), kept in a new `shared/mac-only-capabilities.ts` and mirrored in Swift the way `BotComputers` is, is `macos`; anything else is automatic.  Reachability: the host's last heartbeat is within the window.  Budget: the host's own last heartbeat said admit, with its reason; the controller never computes another host's budget from its own copy of the numbers, and a stale verdict is not eligible.  Caps: the host is under its running cap.

Order and overflow.  Server First prefers the server for an eligible job; when the server is ineligible on budget and overflow is on, the Mac is next, and `placedReason` records "server at its memory budget" or "server unreachable".  This Mac First prefers the Mac and uses the server only when the Mac's RAM or disk gate refuses.  Mac-only capabilities never consider the server.  When no host is eligible the job stays queued with `queuedReason` naming each host's reason ("server: memory budget; Mac: swap 98%").  Nothing is loosened to place a job: a budget is read, never adjusted, by the placer.

What the harness exposes, served by the Node harness on the server, by the Node harness on the Mac in its worker role before BF-2514, and by the Swift engine after it.  `GET /api/placement/identity` returns `{ hostId, platform, version, capabilities, controllerId, epoch }`; `POST /api/placement/register` takes `{ controllerId, epoch, role, capabilities, sample }` and answers accepted or the receiver's pair; `POST /api/placement/heartbeat` takes `{ epoch, leases, admission, sample }` and answers `{ epoch, pendingStops }`; `POST /api/placement/claim` is the compare-and-set lease (the worker pulls); `POST /api/placement/dispatch` is the controller's push for a worker that is connected, idempotent on job id; `POST /api/placement/stop`, `POST /api/placement/report` (idempotent on job id), `POST /api/placement/takeover` (epoch N+1) and `POST /api/placement/release`; `GET /api/placement/jobs` for the UI's cached view; `GET /api/host/resources` for detected capacity, current use, effective thresholds, capabilities and the enforcement state per resource; `GET` and `PUT /api/resources/<hostId>` for the profile with saved and applied.  `/api/health` gains `hostId` and `version` so the handshake has something to compare.  Routes live behind the owner gate on the server and the loopback owner lane on the Mac.  The Swift mirror is one file beside `Jobs.swift`, and a contract test runs the same fixture frames through both decoders, the `EngineReplayHarness` pattern.

Which credential the Mac worker holds against the server is BF-2510's seam: today every loopback caller is the owner and the owner gate admits only the owner credential, so a Mac worker would hold the owner credential unless a worker-scoped token class is added.  The plan leaves that seam open, recommends the worker token class, and names it in the risks.

Coordination with BF-2513: a routine's `runOn` is `bot` or `cloud` (`shared/run-on.ts:10`) and says where tools act, not which host runs the turn; the placement host is a separate field, so a routine can run on the server and still act on the bot's cloud computer.

## Headroom Profiles And What The UI May Say

Types, shared in `shared/placement.ts` and mirrored in Swift: `HostProfile { id, displayName, platform, capabilities, headroomSaved, headroomApplied, appliedAt, enforcement per resource, lastSample, lastSeen }`; `HeadroomSettings { reservedCpuCores?, reservedRamBytes?, minFreeDiskBytes?, minFreeInodes?, minMemoryAvailablePercent? }` where nil means "Not set" and the built-in gates apply; `EnforcementState` as exactly `kernelCap`, `stopWhenOver`, `gateOnly`, `unsupported(reason)` or `notApplied(reason, restartRequired)`; `CapacitySample` with cores, load per core, RAM, memory pressure, swap, disk, inodes, data-volume mount identity and root-disk free.  The Mac profile may not carry a CPU admission cutoff at all; `reservedCpuCores` exists on the server only.

Saved versus applied.  "Saved" is the value in the store with its time.  "Applied" is what the runtime read back after applying: for a cgroup, the file's content from the harness's own cgroup (`/proc/self/cgroup`); for a gate, the threshold the probe is using.  Applied is never copied from saved and never read from a drop-in file.  A server whose unit still says `MemoryMax=infinity` shows "Not applied" however many times the person saved.

Where each profile lives.  The server's headroom is knobs in `server/knob-map.ts` under a new headroom section (`BOTFLEET_JOBS_RESERVED_CPU_CORES`, `BOTFLEET_JOBS_RESERVED_RAM_MB`, `BOTFLEET_JOBS_MIN_FREE_INODES`, `BOTFLEET_JOBS_MIN_MEMORY_AVAILABLE_PERCENT`), because Infisical is the server's sole source of truth and a PUT from the Mac writes through as `PUT /api/config` already does (`server/knob-write-through.ts` refuses the save if the vault write fails).  The Mac's headroom lives in the native store, because a Mac-only user has no vault, and before BF-2515 also reaches the local harness through `PATCH /api/config`, which applies `jobs` keys live.  The two profiles are independent, as the owner asked, and the Mac keeps no copy of the server's profile.

What each host can enforce today, and the only sentences the UI may show.  `kernelCap` reads "Enforced by the system (<mechanism>)"; `stopWhenOver` reads "Watched: jobs are stopped if they exceed it"; `gateOnly` reads "Checked before each job starts"; `unsupported` reads "Not enforced on this <Mac|server>: <reason>"; `notApplied` reads "Saved, applies after the server restarts" or "Saved, could not apply: <reason>".  The words "limit" and "cap" appear only on a `kernelCap` row.

- The Mac today: CPU "Full speed allowed.  Jobs run at background priority (nice, taskpolicy utility) and each job has a CPU-time limit per process", with no reserved field, because BF-2544 forbids a CPU-only cutoff on the Mac and the runner already does exactly that; memory and swap "Checked before each job starts" (the swap gate); disk "Checked before each job starts"; inodes and I/O "Not enforced on this Mac".  macOS has no kernel cap for a process tree's aggregate memory (RLIMIT_RSS is not enforced, RLIMIT_AS breaks Metal and JIT, LaunchAgent plists carry no memory limit), so a Mac memory row may never read "Enforced by the system".  What the Mac can add: a memory-pressure gate (`kern.memorystatus_level` and `vm.swapusage` on the Node side, `DispatchSource` memory-pressure events on the Swift side) beside the swap gate, and a watchdog that sums resident memory across the job's process group on the registry tick (`ps -o pid,pgid,rss`, or the process table `ProcessSupervisorActor.swift:768-834` already walks) and stops the newest over-budget job with SIGTERM then SIGKILL, which earns "Watched: jobs are stopped if they exceed it".  The Mac's defaults must leave room for what the Mac already reserves: OrbStack at 3 CPUs and 4 GiB on the 16 GB Mac, with the Local VM inside that, so the inventory for the Mac records those reservations and no default may exceed what remains.
- The server today: every row "Checked before each job starts" (swap and disk) or "Not enforced on this server" (CPU beyond `nice`, inodes, I/O).  What the server can enforce once the unit says so: `CPUQuota`, `MemoryHigh`, `MemoryMax`, `MemorySwapMax`, `IOWeight` and `TasksMax` over every process in the unit's cgroup, which holds the harness and every tool it spawns (children stay in the service cgroup whatever `KillMode` says; `KillMode=mixed` only decides that SIGTERM goes to the main process first).  Those are `kernelCap` with the applied value read from the cgroup files.  Until per-job cgroups exist, a service-level `MemoryMax` covers the coordinator too, so the OOM killer may take the harness rather than a job, and the honest label is "Enforced by the system (systemd, includes the server process)", with `MemoryHigh` set below `MemoryMax` so throttling comes before the kill.  Two gaps the UI must name: Docker and containerd are active on the host, so a container started through the daemon lands outside the unit's cgroup and the aggregate is understated whenever bots use containers on the server (fix: `--cgroup-parent` under the unit or a `systemd-run` scope); and a disk quota per worker tree needs the ext4 project feature and a `prjquota` remount, a root maintenance window for Jay, so disk on the server stays a gate plus a watcher.  Isolating the coordinator from a runaway job needs a per-job transient scope: `systemd-run` with polkit or a lingering user manager, or `Delegate=yes` with the harness writing a child cgroup per job (`memory.max`, `cpu.max`, `pids.max`, `io.max`), which conflicts with the unit's `ProtectControlGroups=yes` and would mean relaxing one hardening line to gain a real cap, a trade for Jay to see.  Three apply paths, each to be measured before the UI claims it: a root drop-in at install or update (works, needs a restart, so the UI says "Restart the server to apply"); `systemctl set-property` (applies at once, but the harness runs as the service user and would need a polkit rule or a tiny privileged helper); `Delegate=yes` with per-job sub-cgroups.  The drop-in path lands first because it works without a question.

Measured inventory first, as the owner said.  Before any number goes into a default or a drop-in: the server's cores, RAM, swap, volume size, inodes and I/O; the baseline demand of the other apps on the host (the Coolify stack, Qdrant, the TEI services and the Socratic.Trade and Usage Monitor workers run there today); the seven-day peak from the resource-watch samples; the Mac's cores, RAM, ordinary swap level (the admission header records it near 90 to 94 percent in normal use, which is why 98 is the gate), disk and the OrbStack reservation.  A read-only `scripts/host-inventory.mjs` prints those from the existing samples and is the first deliverable; it needs Jay's yes to run read-only on both hosts.  Until it lands every reserved field reads "Not set" and names the current default in force ("swap at or above 98 percent refuses new jobs", "less than 2 GB free refuses new jobs"), labelled as a current default and not a measured value.

Validation copy.  Reserved at or above detected: "This leaves BotFleet no capacity on <host>.  New jobs will wait here until you lower it" (allowed, honest and reversible).  Negative, non-numeric or absent after an edit: "Enter a number of cores / GB / MB", and the previous applied value stays in force; an absent or invalid value never means unlimited.  A value below the built-in gate: "Below the built-in safety gate (<gate>)".  A missing data volume: a red row "Data volume /mnt/fleet-extra is not mounted.  BotFleet has stopped admitting jobs there and is not writing to the root disk."  Every number carries its unit.

One deliberate change for the server in a server mode: today an unknown reading admits ("a broken probe must not switch jobs off", `admission.ts:82-88`).  BF-2544 says not to overcommit because a value is absent, so the server's probe fails closed to `queued` with the reason "Server capacity unknown", while the Mac keeps admitting on unknown so a broken probe cannot switch a Mac-only install off.

## Storage Isolation On The Server

The sandbox already makes a write outside `/mnt/fleet-extra` fail at the kernel.  It does not cover a runtime unmount: if the volume goes away while the unit runs, `/mnt/fleet-extra` is an empty directory on the root filesystem and still inside `ReadWritePaths`, so writes would land on root.  The fix is a device guard at boot and on every sample (the data directory's `st_dev` must differ from root's, which is 2064 against 2049 on the host today), which refuses to start with a named exit code and the log line "data dir <path> is on the root device; refusing to start", parks every job, stops the log and the spool, and shows "Server storage offline" in the Mac UI when it fails at run time, plus `RequiresMountsFor=/mnt/fleet-extra` and `ConditionPathIsMountPoint=/mnt/fleet-extra` in the unit so a boot without the volume never starts the harness (`nofail` in fstab means the boot itself proceeds).  Two more bounds the owner text asks for and the unit lacks: `PrivateTmp` lives on root, so a tool that writes `/tmp` instead of `TMPDIR` consumes root disk (bound it with a size-limited tmpfs or point it at the volume), and `server.log` under `StandardOutput=append:` never rotates because `/etc/logrotate.d` has no botfleet rule.  Inode exhaustion needs the `minFreeInodes` gate, which the probe does not read today.  Root-disk headroom is sampled too, as the owner asked; the Oct 29 root-disk incident on this host (OPS-1006) is the live example.

12. Does the Infisical enrollment path (`BOTFLEET_SERVER_MODE`, `BOTFLEET_SERVER_URL` and the gate token under `/botfleet-server`) stay as an optional seed for enrolled Macs, or is Settings the only way to add a server in the native app?  The native resolver defines only the vault scope today.
13. The webhook wake hold at load three times the core count (`server/resource-triggers.ts:224-233`) is a saturation signal on wakes, not a low-utilization job cutoff.  Keep it under the Mac CPU policy, or remove it?

## Risks

- The Mac worker before BF-2514 is the Node harness in a worker role, and the Swift worker after it is unfunded until question 5 is answered; landing slice 9 and never funding the Swift worker would leave Server First tied to the stack BF-2514 retires.
- Two implementations of one wire contract drift unless both decode the same fixture frames in CI.
- The epoch fence is small and total: a bug that lets a lower-epoch message act is the split brain the design exists to prevent.  Recipes 7 and 8 belong in the required CI gate, not optional smoke.
- Two admitters: if the Mac harness in Server First ever calls its own registry for an unpinned bot, two controllers exist.  The forwarding sits behind the stored mode with a test that the local spawn counter stays zero in worker mode.
- Queueing changes bot-visible behaviour: `job_start` can return `queued` where it used to refuse, and `job_output`'s status line must carry `queuedReason`, or bots will retry and flood the queue.
- No automatic requeue means a dead Mac strands its jobs in `worker-unreachable` until a person clicks Mark Lost.  That is the right trade under the owner's text, and it must be visible or it reads as a hang.
- A person who re-submits by hand a job still running on an unreachable server gets two results for one intent; the UI should warn when a hand re-submission matches a server-owned job by label and thread.
- The Mac RAM watcher is a sampler, not a cap: a fast allocator can pass the budget between samples, summing resident memory double-counts shared pages, and the sampling interval under a load of 100 or more is unmeasured.
- A service-level `MemoryMax` can OOM-kill the harness instead of a job until slice 10b lands; `MemoryHigh` before `MemoryMax` and the "includes the server process" label are the mitigation.
- Relaxing `ProtectControlGroups` and adding `Delegate=yes` widens the unit's sandbox; the review is recorded and a test proves the harness writes only under its own cgroup path.
- Containers on the server sit outside the unit's cgroup unless the runtime is placed under it; I/O limits may not be enforceable on the volume's device; disk quotas depend on the filesystem.  Disk and I/O may remain gates on the server for a long time, and the UI must keep saying so.
- A runtime unmount of `/mnt/fleet-extra` turns the mount point into a writable directory on root inside `ReadWritePaths` until the device guard lands; `PrivateTmp` lives on root; `server.log` never rotates.  `RequiresMountsFor` and the device check keep the server down when the volume is late or missing, which is intended, so the log line names the cause and the fix.
- Infisical write-through for the server profile makes a vault outage block a headroom save; the UI must show the refusal verbatim and keep the previous value.
- Failing closed on an unknown server probe is a behaviour change from today's admit-on-unknown; a broken server probe parks every eligible job in a server mode until noticed.
- Saved versus applied drift is real: `jobs` config applies live in Node, a cgroup drop-in applies on restart, and a mode write waits on the local harness; the UI shows both values and the reason whenever they differ.
- People coming from the Electron remote mode expect the Mac to run nothing; the overflow toggle and migration copy carry that expectation.
- Control's `control-hosts.json` carries the server token in the JSON; the import must move it to the Keychain and rewrite the file, and a failed import must not leave two copies.  Two writable saved-server lists must never exist.
- The Mac-only command table can be wrong in both directions; the explicit pin and the This Mac grant override it, and the reason string says which rule placed the job.
- A merged job list from two harnesses can show a stale server-owned row after a disconnect; rows carry a last-seen time and the status line says unreachable since when.
- UI strings in Swift must carry the sentence gap as `"\u{00A0} "`; a plain two-space string collapses in SwiftUI text.

## Not In This Plan

The production wiring of the native companion API (BF-2511, reopened); the scheduler's own placement field (BF-2513); the version and build numbering policy of Oct 29 (BF-2588); the Muster acceptance (AFC-576); any live change on either host, including the server's unit, its drop-ins, the Mac's LaunchAgents or the Local VM; and any numeric budget.
