Status: draft for review, Thu, Oct 29, 2026.  Owner issue BF-2559 (plan only; the implementation owner is Jay's call).  Refs BF-2544, BF-2514, BF-2515, BF-2510, BF-2528, BF-2531, BF-2513.  Written from the tree at main 7c49bc95 and from read-only facts gathered on fleet-hetzner-nbg1 at 2:21 PM.

## The Modes

Three modes, shown as one radio group under Settings › Servers titled "Where Bots Run".  A mode fixes who the controller is and which hosts may run work; nothing else about ownership is decided at run time.

- **This Mac Only** (`localOnly`), the default on every install.  Controller and worker are this Mac.  No server is contacted, no pairing, no account, no vault bootstrap.  The word "server" appears nowhere outside Settings › Servers until the person adds one.  This is the BF-2544 acceptance: a fresh install completes normal jobs with no server configured.
- **Server First** (`serverFirst`).  Controller: the chosen server.  Workers: the server and this Mac.  The server keeps every placeable job's record and keeps dispatching while the Mac sleeps, which is why Jay wants it.  This Mac runs Mac-only work, work pinned to it, and overflow when the server is at its budget.  In this mode the Mac never admits a placeable job on its own.
- **This Mac First** (`macFirst`).  Controller: this Mac.  Workers: this Mac and the server.  Eligible jobs go to the server only when this Mac's RAM or disk gate refuses them, which is the literal "offload some of the Mac".  When the Mac sleeps nothing is dispatched; that is the honest cost of keeping the record on the Mac.  In this mode the server never admits a job on its own.

Enablement.  The two server rows are always visible and disabled until a saved server has passed the handshake (identity, host id, version, auth, capabilities).  With no saved server the caption reads "Add a server to use this mode."  With a server never reached: "Test <name> below to use this mode."  With a server older than the minimum this app speaks: "<name> is older than this app.  Update the server to use this mode."  The same rule holds on the API, so no script can set a mode the UI refuses.  Remove Server is refused while that server is the controller or holds a lease, with the reason.

Pinning.  Independent of the mode, every bot and every job keeps "Run on: Automatic / This Mac / <server>".  A pin to a host that cannot run the job's capabilities is refused at save time with the reason ("Desktop control only runs on this Mac").  BF-2544 asks for explicit placement first, and pins are that.

Placeable work in version one: background jobs (`job_start`, `server/jobs/registry.ts`) and unattended routine and webhook runs.  Interactive turns stay on the host the person is talking to.  A running job never moves between hosts; transfer happens only at a job boundary, which here means a job finishes where it is and the next one is placed fresh.

Transitions.  The mode record is `{ mode, controllerId, epoch, serverId }`, persisted on both hosts (the Mac in `DatabaseService`, the server beside `jobs.json` with `writeFileAtomic`).

1. `localOnly` to `macFirst`: needs a verified server; the Mac stays controller, the epoch does not change, the server is told it is a worker for controller `<macId>` at epoch N.  No job moves; allowed with work in flight because ownership does not change.
2. `macFirst` to `localOnly`: needs no server lease active, or the person stops those jobs first ("Finish or stop 3 jobs running on the server first").  The server's worker registration is cleared.
3. `localOnly` or `macFirst` to `serverFirst`: needs a verified server and no Mac-owned active job (the same fence `/api/system/control/stop` applies).  In order: the Mac writes "handoff pending"; the server writes `{ controller: server, epoch: N+1 }` and acknowledges; the Mac writes the same and registers as a worker.  On a lost acknowledgement the Mac asks the server for its `{ controllerId, epoch }` and converges to it.
4. `serverFirst` to `macFirst` or `localOnly`, clean: the server is reachable and no server-owned job is active on either worker, or the person stops them.  The server writes "released at N+1" and refuses new `job_start`; the Mac writes `{ controller: mac, epoch: N+1 }`; the server confirms as a worker or detaches.
5. `serverFirst` to `localOnly`, forced ("Take Over On This Mac…" while the server is unreachable): the one transition that may leave work behind, so it is visible and deliberate.  The dialog lists the server-owned jobs last known running there as "will keep running on the server and be shown as orphaned until it returns"; the Mac writes epoch N+1; any later message from the server at epoch N is refused.  When the server returns it reads the higher epoch, demotes itself, stops admitting, finishes or stops its jobs on request, and reports them; the Mac shows them as "finished on the server after takeover" and never reruns them.
6. Server unreachable and reachable again inside `serverFirst` is a connection state, not a mode change.

Every transition is logged with the epoch before and after, and the Settings status row shows "Server First since 2:14 PM (epoch 7)" so two hosts' logs line up.

What changes from the Electron remote mode: that mode made the Mac run nothing and refused credential writes in the app (`electron/remote-credential-guard.mjs`).  Server First is not that: Mac-only work stays on the Mac, so the credential rule becomes per host ("Keys for work that runs on <server> are set on that server", shown in Settings › Models when a server is saved).  Migration: `local` maps to `localOnly`; `remote` maps to `serverFirst` with the vault URL as the one saved server; the Infisical bootstrap stays optional and is never required for the Mac-only path.

## Ownership And The Split-Brain Fence

One record per job, in the controller's store and nowhere else; a worker holds a lease, never a record it can act on alone.  The record extends today's `JobSnapshot` (`shared/jobs.ts:40-71`, mirrored in `ios/Sources/CompanionCore/Jobs.swift`) with `host`, `leaseId`, `epoch`, `placedReason` and `queuedReason`, and two new statuses, `queued` and `worker-unreachable`.  Swift already decodes unknown status values to `.unknown` (`Jobs.swift:19-27`), so an older phone never fails on a new state.  `server/job-host.ts:1-8` already states the rule for delegated turns, an assignment written before anything runs and a cut turn rerun once unless it acted outward; placement keeps that rule and adds the host.

States: `queued` (admitted, no host yet; `queuedReason` says why it waits), `dispatching(host)` (host and lease written in the same transaction as the state, the dispatch message sent after the write), `running(host)` (the worker acknowledged with its pid), `stopping(host)`, `worker-unreachable(host)` (a missed heartbeat window; the job is not requeued), and the terminal `completed`, `failed`, `killed`, `lost`.  `worker-unreachable` leaves only by the worker's own report or by the visible owner action "Mark Lost", optionally "and start again", which makes a new job id and never reuses the old one.

The fence.  Both hosts persist `{ controllerId, epoch }`.  Every placement message carries the sender's epoch.  A receiver refuses a lower epoch and answers with its own pair, so the sender converges instead of acting.  A worker runs a lease only when the lease's epoch equals its stored epoch.  The epoch increments only on a controller change (transitions 3, 4 and 5), so two controllers can never both hold the current epoch.

No duplicate execution, four rules, each checkable: a dispatch is idempotent on job id (a worker that already holds `leaseId` for job X answers the same acknowledgement and does not spawn; a different `leaseId` for X is refused and reported, because the controller lost state and a person must look); a completion report is idempotent on job id; the controller never requeues a dispatched job on a timer or on heartbeat loss; starting again is always a new job id.  The fixture for all four is a job that writes a nonce file, and the assertion is one file after every fault.

Reconnect.  Each worker heartbeats `{ epoch, running lease ids, admission verdict with reason, capacity sample }` on a short interval, and the controller marks it unreachable after a missed window and back on the next heartbeat.  A restarted worker settles each leased job from its exit file, the registry's `adopt()` pattern (`server/jobs/registry.ts:1172-1223`), and reports every result before accepting a new lease.  A restarted controller leaves `dispatching` and `running` records alone until each worker's first heartbeat.  The Mac worker keeps a small on-disk spool of unsent reports keyed by job id, in the shape of `server/zulip/outgoing-spool.ts`, and drains it on reconnect; a spool of results for jobs the controller owns is a worker's outbox, not a second queue.  If the server's host id in the handshake differs from the saved one, the app stops and says "This is a different server than the one you added".

Server unreachable in Server First (`serverFirst.disconnected`).  Mac-worker jobs continue and their results spool.  A bot's `job_start` is refused with "The server that owns jobs has been unreachable since 2:14 PM.  Run the command with bash if it is short, tell the user, or the user can switch to This Mac Only in Settings", the same refuse-with-reason contract admission already uses (`admission.ts:148-166`).  Routine runs due in that window are recorded as "skipped: server unreachable" rather than run locally.  The menubar and Settings say the same sentence.  Nothing is admitted locally, so no second controller appears by accident; the deliberate way out is transition 5.  A local list of waiting jobs was considered and rejected, because it is a queue outside the authoritative one.

Server unreachable in This Mac First.  The Mac is still the controller: new jobs keep being placed on the Mac when eligible, server-leased jobs go to `worker-unreachable`.

Why no automatic failover.  Promoting the Mac while the server is merely slow is the one design that can produce two controllers at the same epoch for a window, which the owner text names as the thing not to do.  A visible forced takeover with an epoch bump gives the person the same capability with a fence.

GB-Oracle's checks, answered: every job has exactly one owner in every mode (the record lives on the controller, the worker holds a lease); SQLite writes stay local to one host (the controller writes its own store, the worker writes its own log, exit file and spool, and no host opens another host's database); the server's update and rollback path is `deploy/linux-server/update.sh` and the retention contract in `docs/native-rewrite-linux-source-retention.md`, with the `linux-server-preservation` evidence key from #1403 gating the decommission.

## The Placement Contract

One authoritative queue, the controller's.  A `job_start` on any host in a server mode becomes a request to the controller; the controller admits, writes the record as `queued`, then places.  The per-thread and per-bot caps stay refusals, because they are about the bot; the per-host cap becomes an eligibility input, so a job no host can take right now is queued with a reason rather than refused.  `job_start` returns `{ ok: true, job: { status: "queued", queuedReason } }` and its notice tells the bot to wait or use bash for something short.  Whether This Mac Only also queues past its cap is an open question below.

Eligibility, in order.  Capability: the job's required set must be a subset of the host's.  Required capabilities come from the pin and from derivation the controller can do without guessing: a cwd under the Mac's home is `homeWorkspace`; a bot holding the This Mac computer grant (`BotComputers.swift:13-18`) is `desktop`; a command whose first word is `xcodebuild`, `xcrun`, `simctl`, `osascript` or `open` is `macos`; anything else is automatic.  Reachability: the host's last heartbeat is within the window.  Budget: the host's own last heartbeat said admit, with its reason; the controller never computes another host's budget from its own copy of the numbers, and a stale verdict is not eligible.  Caps: the host is under its running cap.

Order and overflow.  Server First prefers the server for an eligible job; when the server is ineligible on budget the Mac is next, and `placedReason` records "server at its memory budget" or "server unreachable".  This Mac First prefers the Mac and uses the server only when the Mac's RAM or disk gate refuses.  Mac-only capabilities never consider the server.  When no host is eligible the job stays queued with `queuedReason` naming each host's reason ("server: memory budget; Mac: swap 98%") and is re-evaluated on every heartbeat and on every job end, oldest first within a bot.  Nothing is loosened to place a job: a budget is read, never adjusted, by the placer.

What the harness exposes, served by the Node harness on the server and by the native engine on the Mac, so the Mac worker loop is one piece of code against either.  `GET /api/placement/identity` returns `{ hostId, platform, version, capabilities, controllerId, epoch }`; `POST /api/placement/register` takes `{ controllerId, epoch, role }` and answers accepted or the receiver's pair; `POST /api/placement/heartbeat` takes `{ epoch, leases, admission, sample }` and answers `{ epoch, pendingStops }`; `POST /api/placement/dispatch` takes `{ epoch, lease, jobSpec }` and answers `{ acknowledged, pid }`, idempotent on job id; `POST /api/placement/stop`, `POST /api/placement/report` (idempotent on job id), `POST /api/placement/takeover` (epoch N+1) and `POST /api/placement/release`; `GET /api/placement/jobs` for the UI's cached view; `GET` and `PUT /api/resources/<hostId>` for the profile with saved, applied and enforcement.  `/api/health` gains `hostId` and `version` so the handshake has something to compare; today it carries `app`, `ready` and `pid` only, which is the identity check Control makes (`ControlAPI.swift:159-167`).  The Swift mirror is one file beside `Jobs.swift`, and a contract test runs the same fixture frames through both decoders, the `EngineReplayHarness` pattern.

Which port and credential the Mac worker uses to reach the server is BF-2510's seam: today every loopback caller is the owner and the owner gate on 8798 admits only the owner credential (`deploy/linux-server/README.md`, `owner-gate.mjs:11-20, 201, 243`), so a Mac worker would hold the owner credential unless a worker-scoped token class is added.  The plan leaves that seam open and names it in the risks.

Coordination with BF-2513: a routine's `runOn` is `bot` or `cloud` (`shared/run-on.ts:10`) and says where tools act, not which host runs the turn; the placement host is a separate field, so a routine can run on the server and still act on the bot's cloud computer.

## Headroom Profiles And What The UI May Say

Types, shared in `shared/placement.ts` and mirrored in Swift: `HostId` ("mac:<installUUID>" or "server:<serverUUID>"); `HostProfile { id, displayName, platform, capabilities, headroomSaved, headroomApplied, appliedAt, enforcement per resource, lastSample, lastSeen }`; `HeadroomSettings { reservedCpuCores?, reservedRamBytes?, minFreeDiskBytes?, minFreeInodes? }` where nil means "Not set" and the built-in gates apply; `EnforcementState` as exactly `kernelCap`, `stopWhenOver`, `gateOnly`, `unsupported(reason)` or `notApplied(reason, restartRequired)`; `CapacitySample` extending `sampleHost` in `server/resource-triggers.ts` with inodes, memory pressure and mount identity.  The Mac profile may not carry a CPU admission cutoff at all; `reservedCpuCores` on the Mac sizes the scheduling priority message and never refuses a job.

Saved versus applied.  "Saved" is the value in the store with its time.  "Applied" is what the runtime read back after applying: for a cgroup, the file's content; for a gate, the threshold the probe is using.  Applied is never copied from saved.  A server whose unit still says `MemoryMax=infinity` shows "Not applied" however many times the person saved.

Where each profile lives.  The server's headroom is knobs in `server/knob-map.ts` under a new headroom section (`BOTFLEET_HEADROOM_RESERVED_CPU_CORES`, `BOTFLEET_HEADROOM_RESERVED_RAM_MB`, `BOTFLEET_HEADROOM_MIN_FREE_DISK_MB`, `BOTFLEET_HEADROOM_MIN_FREE_INODES`), because Infisical is the server's sole source of truth and a PUT from the Mac writes through as `PUT /api/config` already does.  The Mac's headroom lives in the native store, because a Mac-only user has no vault.  The two profiles are independent, as the owner asked.

What each host can enforce today, and the only sentences the UI may show.  `kernelCap` reads "Enforced by the system"; `stopWhenOver` reads "Watched: jobs are stopped if they exceed it"; `gateOnly` reads "Checked before each job starts"; `unsupported` reads "Not enforced on this <Mac|server>"; `notApplied` reads "Saved, applies after the server restarts" or "Saved, could not apply: <reason>".  The words "limit" and "cap" appear only on a `kernelCap` row.

- The Mac today: CPU "Full speed allowed.  Jobs run at background priority (nice, taskpolicy utility)", with no reserved field, because BF-2544 forbids a CPU-only cutoff on the Mac and the runner already does exactly that; CPU time per job is enforced by `ulimit -t`; memory and swap "Checked before each job starts" (the swap gate); disk "Checked before each job starts"; inodes and I/O "Not enforced on this Mac".  macOS has no kernel cap for a process tree's aggregate memory (RLIMIT_RSS is not enforced, RLIMIT_AS is unreliable, LaunchAgent plists carry no memory limit), so a Mac memory row may never read "Enforced by the system".  What the Mac can add: a memory-pressure gate from `kern.memorystatus_vm_pressure_level` beside the swap gate, and a watchdog that sums `phys_footprint` across the job's process group and stops the newest over-budget job with SIGTERM then SIGKILL, which earns "Watched: jobs are stopped if they exceed it".  The Mac's defaults must leave room for what the Mac already reserves: OrbStack at 3 CPUs and 4 GiB on the 16 GB Mac, with the Local VM inside that, so the inventory for the Mac records those reservations and no default may exceed what remains.
- The server today: every row "Checked before each job starts" (swap and disk) or "Not enforced on this server" (CPU beyond `nice`, inodes, I/O).  What the server can enforce once the unit says so: `CPUQuota`, `MemoryHigh`, `MemoryMax`, `MemorySwapMax`, `IOWeight` and `TasksMax` over every process in the unit's cgroup, which is the whole harness and every tool it spawns because `KillMode=mixed` keeps children in the unit; those are `kernelCap` with the applied value read from the cgroup files.  Two gaps the UI must name: a container started through a Docker daemon lands in Docker's cgroup, not the unit's (whether bots on the server use containers was not checked), and a disk quota per worker tree needs the ext4 project feature and a `prjquota` remount, a root maintenance window for Jay, so disk on the server stays a gate plus a watcher.  A unit-level cap protects the host's other apps but not the coordinator from a runaway job; a per-job transient scope needs either `systemd-run` with polkit or a lingering user manager, or `Delegate=yes`, which conflicts with the unit's `ProtectControlGroups=yes` and would mean relaxing one hardening line to gain a real cap, a trade for Jay to see.  Three apply paths, each to be measured before the UI claims it: a root drop-in at install or update (works, needs a restart, so the UI says "Restart the server to apply"); `systemctl set-property` (applies at once, but the harness runs as the service user and would need a polkit rule or a tiny privileged helper); `Delegate=yes` with per-job sub-cgroups.  The drop-in path lands first because it works without a question.

Measured inventory first, as the owner said.  Before any number goes into a default or a drop-in: the server's cores, RAM, swap, volume size, inodes and I/O; the baseline demand of the other apps on the host (the Coolify stack, Qdrant, the TEI services and the Socratic.Trade and Usage Monitor workers run there today); the seven-day peak from the resource-watch samples; the Mac's cores, RAM, ordinary swap level (the admission header records it near 90 to 94 percent in normal use, which is why 98 is the gate), disk and the OrbStack reservation.  A read-only `scripts/host-inventory.mjs` prints those from the existing samples and is the first deliverable; it needs Jay's yes to run read-only on both hosts.  Until it lands every reserved field reads "Not set" and the existing gates are the only defaults.

Validation copy.  Reserved at or above detected: "This leaves BotFleet no capacity on <host>.  New jobs will wait here until you lower it" (allowed, honest and reversible).  Negative, non-numeric or absent after an edit: "Enter a number of cores / GB / MB", and the previous applied value stays in force; an absent or invalid value never means unlimited.  A value below the built-in gate: "Below the built-in safety gate (<gate>)".  A missing data volume: a red row "Data volume /mnt/fleet-extra is not mounted.  BotFleet has stopped admitting jobs there and is not writing to the root disk."  Every number carries its unit.

One deliberate change for the server in a server mode: today an unknown reading admits ("a broken probe must not switch jobs off", `admission.ts:82-88`).  BF-2544 says not to overcommit because a value is absent, so the server's probe fails closed to `queued` with the reason "Server capacity unknown", while the Mac keeps admitting on unknown so a broken probe cannot switch a Mac-only install off.

## Storage Isolation On The Server

The sandbox already makes a write outside `/mnt/fleet-extra` fail at the kernel.  It does not cover a runtime unmount: if the volume goes away while the unit runs, `/mnt/fleet-extra` is an empty directory on the root filesystem and still inside `ReadWritePaths`, so writes would land on root.  The fix is a device guard at boot and on every sample (the data directory's `st_dev` must differ from root's), which parks every job, stops the log and the spool, and shows "Server storage offline" in the Mac UI when it fails, plus `RequiresMountsFor=/mnt/fleet-extra` and `ConditionPathIsMountPoint=/mnt/fleet-extra` in the unit so a boot without the volume never starts the harness (`nofail` in fstab means the boot itself proceeds).  Two more bounds the owner text asks for and the unit lacks: `PrivateTmp` lives on root, so a tool that writes `/tmp` instead of `TMPDIR` consumes root disk (bound it with a size-limited tmpfs or point it at the volume), and `StandardOutput=append:` on `server.log` never rotates (whether logrotate exists on the host is not checked).  Inode exhaustion needs the `minFreeInodes` gate from `statfs`, which the probe does not read today (`admission.ts:131-138` reads `bavail` and `bsize` only).  Root-disk headroom is sampled too, as the owner asked; the Oct 29 root-disk incident on this host (OPS-1006) is the live example.

## Settings And Menubar

Settings today is a `TabView` over `MacSettingsSection` (general, models, voice, shortcuts, lifecycle, permissions; `ios/Sources/CompanionCore/MacStreamingTranscript.swift:519-538`).  Two sections are added; the free-text Local Harness Address stays until BF-2515 removes the local harness.

Settings › Servers.  The "Where Bots Run" radio group, each row with a one-line caption and the unavailable rows disabled with the reason inline, never hidden.  Then the Servers list, with the empty state "No server added.  BotFleet runs on this Mac.  Add a server if you have one." and "Add a Server…".  The sheet asks for the address and, when the device is not on the tailnet as a logged-in user, a gate token (the gate accepts a Tailscale login header or an `x-botfleet-gate-token` header).  "Test" runs the identity check Control already does plus the host id, version and capability read, and reports "Reached <name>: BotFleet <version> on Linux, <n> cores, <x> GB RAM, <y> GB free on its data volume" or the exact failure.  Save stores the record in the native store and the token in the Keychain, the discipline the iOS `Connection` keeps (`Client.swift:10-12`).  Each row shows name, address, "Reached <time>" or "Unreachable since <time>", the version with "older than this app" when it is, and Remove with its refusal or its consequence ("<n> jobs on <name> keep running there; this Mac will stop showing them").  The status row reads "Server First since 2:14 PM (epoch 7) · server reachable · 3 running (2 server, 1 Mac) · 1 waiting: both hosts over memory budget", or when unreachable "Server First · server unreachable since 2:14 PM · new jobs wait · 1 Mac job still running · Take Over On This Mac…".  The forced takeover lives here and nowhere else.

Settings › Resources.  A host picker, This Mac and each verified server.  One row per resource (CPU, Memory, Swap, Disk on the data volume, Inodes, I/O) with five cells: Detected ("10 cores", "32.0 GB", "412.3 GB free of 1.8 TB"), Reserved for other apps (editable; "Not set" when nil), Effective BotFleet budget (derived, "<detected> − <reserved> = <budget>", "Not limited" when reserved is nil), Current use with its sample time, and the enforcement sentence from `EnforcementState` and nothing else.  Below: "Saved <time> · Applied <time>" or "Saved <time> · Not applied: <reason>", with Apply Now when the runtime can apply without a restart and "Restart the server to apply" when it cannot.  "<n> jobs waiting for room on this host" links to them.

Why a job went where it went.  The controller writes `placedReason` or `queuedReason` when it decides, and every surface shows that one sentence: the thread's job pill ("Queued: both hosts are over their memory budget", "Ran on this Mac: needs xcodebuild", "Ran on this Mac: <server> RAM budget full (<used> of <budget>)", "Waiting: the Mac that runs this has been unreachable since 2:14 PM"), `job_output`'s status line, the menubar's waiting count, and the bot's notice, so the model reads what the person reads.

Menubar.  In This Mac Only, nothing is added except "2 waiting for room" in the status line when any job waits.  In a server mode, one row under the status line: "Server <name>: connected" or "Server <name>: unreachable since <time> · <n> waiting", the latter with a submenu holding "Take Over On This Mac…" and "Open Servers Settings".  The lifecycle rows are the next section's.

Main window banner, in a server mode while the server is unreachable, in the style of the iOS offline advice (`Failover.swift:164-195`): "Can't reach <name> at <host>.  If that is a Tailscale name, this Mac may be off the tailnet.  Work pinned to this Mac keeps running; other new work waits.  Retrying automatically."

Copy rules that bind every string above: units on every number; "Enforced by the system" only for `kernelCap`; no agent seat names; no host name of Jay's in a default; a real U+00A0 plus a space between sentences in Swift literals (`"\u{00A0} "`); times in Central, 12-hour.

## The Native Lifecycle Surface Under Option C

Decision 1 puts the product half of BotFleet Control into the native app.  That is a slice of its own in this plan, because the saved-server list it needs is the same list placement needs.

What moves in: harness status with bot count and blocking work; fenced start and stop (the native app's Shut Down Server & Local VM already uses the fenced route since #1400, and the companion's durable stop and the owner-stops record since #1401 are the model to port); Start Server At Login (the startup policy and a login item); the shared Local VM start and stop; and the saved servers with per-server stop and VM actions.  `SavedServer` replaces Control's `ServerHost`: a one-time import on first launch reads `~/.botfleet/control-hosts.json`, moves each token into the Keychain, rewrites the JSON without tokens, and drops the Hetzner seed, because a product default must not name Jay's server.  After the import has shipped for one release, Control's `ServerHost` and `ServerHostStore` are deleted with the rest of Control's product half.

What moves out, to Muster (AFC-354, Codex's AFC-576 records the acceptance): the twelve-row fleet services list, the pm2 rows, the process and port monitor with orphan kill, and the remote VM providers.  Muster reads BotFleet's processes and VM status; it owns none of them, and BotFleet starts, runs and controls its own VMs with Muster absent or down.  The decommission gate's `control-disposition` evidence is asserted only when both halves have landed and been verified.

## Evidence

Every recipe runs in an isolated fixture: temporary data directories, free ports, `BOTFLEET_DISABLE_CONTAINER_RUNTIME=1`, never port 8799 and never the owner's data (`docs/verification/README.md`).  Two-host recipes start two harness processes on one machine, one in the server role and one in the Mac role, with injected probes and an injectable link so a disconnect is a flag, not a cable.  Recipes land in `docs/verification/placement.md` and `docs/verification/headroom.md`, and a strict state file `placement-evidence.json` is checked by `scripts/check-placement-evidence.mjs`, modeled on `scripts/check-decommission-gates.mjs` with its zod strict schema and its "not asserted" blockers, so BF-2514 and BF-2515 read `placement-evidence` the way they read `control-disposition` and `linux-server-preservation`.  Hand-run recipes record their log path and the Central time they ran.

1. **fresh-mac-only-install.**  One harness, empty data dir, no server.  A job that writes a nonce completes; the mode is `localOnly`; the two server rows are disabled with "Add a server to use this mode."; no request leaves loopback.
2. **server-first-placement.**  Two harnesses; mode `serverFirst`.  An unpinned job runs on the server role with `placedReason` "preferred server"; a Mac-pinned job runs on the Mac role with "needs macos"; the record lives on the server only.
3. **server-saturation-overflow.**  The server probe reports admit no, "memory budget".  The job runs on the Mac with "server at its memory budget"; the server role never spawned.
4. **mac-high-cpu-accepted.**  The Mac sample has load four times its cores with swap at 50 percent: admitted.  Then swap at 98 percent with load near zero: queued with "Mac: swap 98%".  Asserts the Mac profile has no CPU cutoff field.
5. **both-hosts-pressure-queue.**  Both probes refuse; the job is queued with both reasons; one probe clears; exactly one start, oldest first; one nonce file.
6. **disconnect-no-duplicate.**  A long Mac-role job under a server-role lease; the link is cut; `worker-unreachable` appears on the server within the window; the job finishes while cut; the link returns; the spooled report applies once; a replayed dispatch for the same job id answers the same acknowledgement with no second spawn.  Also cut the link during the acknowledgement so the controller resends the same `leaseId`; one spawn.
7. **mode-change-fence.**  A job runs in `localOnly`; `PUT mode=serverFirst` is refused with the sentence; the job finishes; the PUT succeeds with epoch N+1 on both hosts; a third process loaded with the Mac role's pre-switch state at epoch N sends dispatch and report and every message is refused with `{ controllerId, epoch N+1 }`; no spawn anywhere.
8. **forced-takeover-and-return.**  `serverFirst` with a server-owned job running; the link is cut; takeover from the Mac; epoch N+1 and `localOnly` on the Mac; the link returns; the server reads N+1, refuses `job_start` with "this server is no longer the controller", finishes its job, reports it; the Mac shows it as finished on the server after takeover; one nonce file.
9. **settings-saved-vs-applied.**  A profile whose apply path is stubbed to fail: saved time set, applied unchanged, "Not applied: <reason>"; a reservation at or above detected is refused with "Leaves nothing for bots"; an empty value reads "Not set" and admission still refuses at the swap gate with no profile.  Swift view-model tests and `server/config.test.ts`.
10. **headroom-enforced-mac.**  Injected footprint samples for a job tree above the RAM budget: the newest job receives SIGTERM then SIGKILL after the grace, status stopped with "Over the RAM budget (<n> GB of <budget>)", and the badge is `stopWhenOver`, never `kernelCap`.
11. **headroom-enforced-server.**  On an Ubuntu runner, `systemd-run --user --scope -p MemoryMax=<small>` on a memory hog exits 137 with `memory.events oom_kill 1`; `CPUQuota=50%` on a spin loop shows `cpu.stat` near half of wall time.  Hand-run on fleet-hetzner-nbg1 after the drop-in lands: `systemctl show botfleet-server.service -p MemoryMax -p CPUQuotaPerSecUSec -p IOWeight -p TasksMax` prints the configured values, and `GET /api/resources/<server>` reports the same values as applied.
12. **mount-loss-root-fallback.**  Unit test: the device guard with injected stat results parks jobs and reports "Server storage offline".  Hand-run on a throwaway copy of the root on the server: a bind mount over it, a test unit from the template with `RequiresMountsFor` and `ConditionPathIsMountPoint`; systemd refuses to start it and logs the condition; after unmount it starts.  Never against the live unit.
13. **other-apps-unchanged.**  Hand-run on the server with Jay: a neighbouring service's HTTP health probed every second for ten minutes while a saturating job runs inside the capped unit; the probe's p95 stays within the baseline measured before.  This is BF-2544's "unchanged responsiveness of the server's other applications" and cannot be faked in CI.
14. **inventory-recorded.**  The read-only inventory output for both hosts, with the time, is attached before any numeric default is committed; the checker blocks on a numeric default without it.

State file shape, strict: `{ "evidence": { "fresh-mac-only-install": true, …, "other-apps-unchanged": false }, "handRun": { "headroom-enforced-server": { "at": "<Central time>", "log": "<path>" } }, "inventory": { "server": "<path>", "mac": "<path>" } }`.  Anything not asserted blocks, exactly as the decommission checker does.

## Risks

- The Mac worker has nowhere to run yet: the native engine runners, `DatabaseService` and the scheduler exist as tested libraries nothing in `ios/MacApp` instantiates (the Control plan's structural finding).  Slice 4 cannot land before that, and designing the protocol against the Node harness alone could bake in Node assumptions; the shared fixture frames in slice 1 are the mitigation.
- Two implementations of one wire contract drift unless both decode the same fixture frames in CI.
- The epoch fence is small and total: a bug that lets a lower-epoch message act is the split brain the design exists to prevent.  Recipes 7 and 8 belong in the required CI gate, not optional smoke.
- Queueing changes bot-visible behaviour: `job_start` can return `queued` where it used to refuse, and `job_output`'s status line must carry `queuedReason`, or bots will retry and flood the queue.
- No automatic requeue means a dead Mac strands its jobs in `worker-unreachable` until a person clicks Mark Lost.  That is the right trade under the owner's text, and it must be visible or it reads as a hang.
- A person who re-submits by hand a job still running on an unreachable server gets two results for one intent; the UI should warn when a hand re-submission matches a server-owned job by label and thread.
- The Mac RAM watcher is a sampler, not a cap: a fast allocator can pass the budget between samples, summing RSS double-counts shared pages, and the sampling interval under a load of 100 or more is unmeasured.
- Containers on the server sit outside the unit's cgroup unless the runtime is placed under it; I/O limits may not be enforceable on the volume's device; disk quotas depend on the filesystem.  Disk and I/O may remain gates on the server for a long time, and the UI must keep saying so.
- A runtime unmount of `/mnt/fleet-extra` turns the mount point into a writable directory on root inside `ReadWritePaths` until the device guard lands; `PrivateTmp` lives on root; `server.log` never rotates.
- Infisical write-through for the server profile makes a vault outage block a headroom save; the UI must say "Saved locally, not applied to server" and never show a saved value as applied.
- Failing closed on an unknown server probe is a behaviour change from today's admit-on-unknown; a broken server probe parks every eligible job in a server mode until noticed.
- The `Delegate` versus `ProtectControlGroups` interaction and the privilege path for `set-property` are unmeasured; if neither works, every server cap change needs a root restart and Apply Now is never available on the server.
- People coming from the Electron remote mode expect the Mac to run nothing; without migration copy the first Server First user will think routing is broken.
- Control's `control-hosts.json` carries the server token in the JSON; the import must move it to the Keychain and rewrite the file, and a failed import must not leave two copies.  Two writable saved-server lists must never exist.
- The Hetzner seed in `ServerHost.defaultHetzner` is Jay's host name; the import drops it and no default server may ship.
- UI strings in Swift must carry the sentence gap as `"\u{00A0} "`; a plain two-space string collapses in SwiftUI text.
