# Placement Rollback Bridge Source Fixture

Refs BF-2632 and BF-2625.  This recipe verifies the conservative source runtime in isolated temporary data directories and free loopback ports.  It does not prove that a signed, shipped or retained rollback artifact is compatible.  No production data, provider request or placement activation is involved; all sixteen acceptance flags remain false.

Run with the lane's existing dependencies and private compiled Clutch view, without installation:

```sh
node node_modules/typescript/lib/tsc.js -b --pretty false
node node_modules/typescript/lib/tsc.js -p tsconfig.server.json --pretty false
node node_modules/oxlint/bin/oxlint server/placement-readonly.ts server/placement-readonly.test.ts
VITEST=true node node_modules/vitest/vitest.mjs run server/placement-readonly.test.ts server/placement-controller-epochs.test.ts server/jobs/registry.test.ts server/routines.test.ts --maxWorkers=1
git diff --check
```

The focused run passed four files and 190 cases.  Both TypeScript stages and the new reader's scoped lint passed.  The reader cases cover unchanged legacy bootstrap, fresh committed WAL visibility, unchanged database/WAL/marker bytes, closed-ledger reopen, refusal to activate prepared state, unknown schema, missing/orphan authority, changed marker and public-sidecar refusal.

The reader also refuses normalized SQLite on unsupported actual or injected platforms before opening a database, matching the authoritative placement store.  Its negative fixture compares every retained file and mode byte-for-byte after refusal, while a legacy JSON fixture still opens without creating a database or payload namespace.  The combined reader and authority run passed 50 cases after this integration.

Review of the stacked PR found three further passive-runtime gaps.  The bridge now leaves `jobHost` absent instead of opening `runtime.db` and booting its queued dispatcher, refuses updater run before it can replace the pinned binary, and makes direct scheduler mutators inert while passive.  The actual HTTP fixture seeds a queued delegated assignment and verifies that its complete record remains queued after passive boot, then checks owner-authenticated updater run returns 503; the scheduler fixture compares lists, snooze state and file bytes after direct mutation attempts.  The affected three-suite run passed 40 cases.

The passive job cases exercise construction, start, queue drain, adoption, timers, tick, log maintenance, process sweep, owner/system stop, notice delivery, quiesce and synchronous shutdown without modifying records or spawning a process.  Passive scheduler construction preserves a running check-in, and mutating the caller's options cannot release that capability.

The actual HTTP child first proves unchanged legacy epoch transitions, then stops before fixture-only migration.  Its migrated fixture contains reconciliation, an unreachable old issuing lease and pending stop, a settled terminal report and a verified released-lease tombstone.  All ten placement POSTs refuse, a companion request remains forbidden, updater POST/DELETE stay held, a new application mutation refuses, and interrupted-turn plus pending-update evidence survives the recovery delay and restart.  Identity converges on an explicitly committed newer fixture fence; the bridge otherwise leaves the logical authority unchanged.

Independent review found two saved-evidence mutations: ordinary guarded loading could quarantine or rewrite damaged scheduler data before passive construction returned, and connector-status GET could mark room continuations resumed before dispatch refused.  Read-only guarded loading now preserves the complete malformed/partial original and directory entries while recording in-memory fault evidence.  Connector-status GET returns saved observational state without querying a provider, patching a card or resuming it; dispatch, resume and drain also refuse before continuation edits.  General application-store loading retains its existing repair behavior; this bridge does not claim globally immutable application data.

The correction run passed all 28 cases in `server/routines-quarantine.test.ts` and `server/placement-controller-epochs.test.ts`, including both damaged scheduler fixtures and an actual HTTP connected room card whose stored JSON remains byte-for-byte unchanged.  Server TypeScript and scoped correction lint passed.  These targeted checks supplement the earlier 190 cases and do not replace the independent review or full gate.

After independent review confirmed both fixes and no additional actionable finding, preflight passed all nine focused authority/job/scheduler suites with 285 cases, both direct TypeScript stages, the complete lint baseline at 4,867 warnings and the decommission inventory fixture.  The read-only module is covered by the existing placement inventory row, and no acceptance flag or gate predicate changed.  The full bridge test chain follows this clean preflight in a separate preserved receipt, using the unchanged package script expansion and a process-local `022` file mask from before the first child.

The initial full chain passed its first phase and reported 12,728 passed cases with one failed source-wiring assertion in the main suite.  That fixture required `runtimeQuiescing` to be the first statement of `startTurn`, so the preceding immutable bridge fence prevented it from locating the function body.  The test now locates the function's declaration/body boundary independently of the first fence, checks through the actual policy-gated clear and rejects an unrelated function's clear; every original refusal/status/order assertion remains.  All fourteen affected wiring/policy cases, both TypeScript stages and the full lint baseline passed after this test-only correction.  Production source did not change, and the original failure receipt is retained; remaining chain phases run as a separate segment rather than being presented as an uninterrupted green command.

Root review then caught a legacy identity callback bypassing the lease service's observed-fence check.  Legacy identity now calls the service's fresh monotonic reader, while migrated identity retains the separate read-only SQLite reader; authorization still precedes either callback.  The actual HTTP fixture proves a regressed legacy file returns generic 503 without rewriting it, an unauthorized caller stays forbidden, and restoring the verified pair restores identity.  All eighteen epoch/identity cases, server TypeScript and the full lint baseline passed for this narrow source correction after the segmented chain completed.

Integration with the reviewed normalized kernel and its fenced queue-expiry correction preserves current main through `949213a0`.  The only merge conflict was the existing placement inventory row, resolved to one row that includes the read-only reader without changing acceptance flags or gate predicates.  The bridge runtime remains byte-for-byte identical to its reviewed source; the kernel lease/store implementation and store fixtures remain identical to `a21a2f55`.  The combined isolated run passed all 385 cases across fifteen authority, job, scheduler, guarded-store and stop-policy suites, both direct TypeScript stages, the unchanged 4,867-warning lint baseline and all 31 decommission inventory checks.  This bounded integration check supplements the preserved segmented full-chain receipts rather than claiming a new uninterrupted global run.

## Rollback Candidate Inspector And Generated Fixture Probe

Refs BF-2632.  `scripts/placement-rollback-probe.mjs` is the static inspector and the selected-artifact probe runner the plan calls for.  Everything recorded in this section is generated-fixture evidence.  It is not a shipped-runtime pass: no built, signed, shipped or retained BotFleet artifact was inspected or started, no acceptance flag in `docs/verification/placement-evidence.json` changed, and no gate predicate changed.

Run the recipe from a lane with its dependencies installed:

```sh
node --test scripts/placement-rollback-probe.node-test.mjs
pnpm test:native-release
```

The file passed 29 of 29 cases under Node 24.18.0 on Linux.  `pnpm test:native-release` lists it, so the `pnpm test` chain runs it under Node 26.  Both hosted test checks currently run on `ubuntu-latest`, because the check named `macos-latest` is mapped to an Ubuntu runner while the macOS pool is parked (BF-2627).  The file has therefore not been run on macOS anywhere: the process-group teardown, the `/var` to `/private/var` temporary paths and the `node:sqlite` sidecar behavior of its darwin paths are unexercised.  The cases need a Node that strips TypeScript types, because the normalized fixture is prepared by the reviewed migration helper in `server/placement-store.ts`.

Every candidate in that file is generated inside the test: a few files committed to a throwaway repository, exported with `git archive`, and promoted into a release store rooted in a temporary directory.  Its `server/index.ts` is a small stand-in for the bridge's HTTP surface, so a pass proves that the inspector and the recipe behave as specified.  It proves nothing about the real bridge build, which only the source fixture above and a later authorized run against a selected artifact can show.

`inspectPlacementRollbackCandidate(candidate)` takes one explicitly named release directory, its expected source commit, the repository that holds that commit and the physical runtime binary.  It executes nothing and answers only `blocked` or `probe-required`.  It binds the candidate through the release store's strict manifest validation, byte-and-type comparison with the commit's tree objects, the release build identity, a content inventory of the whole physical tree that follows no link out of the release, and a SHA-256 of the runtime file.  Every git read runs with object replacement turned off, so a `refs/replace` entry in the named repository cannot make other bytes bind as the expected commit, and the binding records the physical repository that vouched for the commit.  A release that carries `node_modules` stays `blocked` until a trusted reference tree is named.  A symbolic link is refused for the release directory and for the runtime file itself, a link in a parent directory of the runtime is resolved once and the physical path is what is bound, and only an ELF or Mach-O executable is accepted, so an interpreter script cannot stand in for the program that runs the candidate.  The shared libraries the runtime loads are outside that fingerprint.  The release manifest is read through a handle opened without following a link and checked to be the regular, singly linked file that was listed, and a runtime binary that has another hard link is blocked.  A file is opened without following a link or the inspector refuses, so a platform without that open flag blocks instead of reading.  Before anything is read, hashed, handed to git or started, a candidate path that names or leads into a credential, login or dot directory (the routine policy's list, and any other path component that starts with a dot), or that is a link leading nowhere, is blocked.  The one exception is BotFleet's own application home `.botfleet`, because the release store's default root is `~/.botfleet`.

`runPlacementRollbackFixtureProbe(candidate, options)` is the only path that can answer `fixture-verified`.  It recomputes the same binding itself, and it reads no report, status or flag from its caller.  A caller may lengthen the recovery wait and the stop grace but never shorten them, and no wait may exceed ten minutes: an override outside that range is ignored and named in the receipt, so a shortened run cannot carry the status of a full one.  Recipe version 1 then does the following in a new temporary home, on a free loopback port pair, with the container runtime locked down and one unknown provider driver:

1. Seeds a strict legacy epoch pair, starts the candidate with the selected runtime in the release-store launch shape, and requires identity to report that pair with no SQLite authority and no payload namespace created.
2. Stops the child by process group and requires the group to be gone and both loopback ports to be closed.
3. Prepares the normalized fixture through the migration helper: a nonzero controller fence, reconciliation state, a settled report, an unreachable old issuing lease with a pending stop, and a released-lease tombstone.
4. Starts the candidate again and requires identity to report the stored fence, a companion request to be forbidden, and the ten placement POSTs plus a stale claim, a stale enqueue, a released-lease dispatch and a terminal report replay to be refused with 503.
5. Requires quiesce POST and DELETE to keep the read-only hold, and an application mutation and an updater run to be refused.
6. Waits out the recovery delay and requires the saved resumption evidence, the canonical logical ledger digest and the database, WAL and marker bytes to be unchanged.
7. Has the fixture writer commit a newer fence and requires the same child to converge on it without a restart, to refuse the same requests at the now-stale fence, and to leave the ledger as the writer left it.
8. Stops the child the same way and compares the ledger once more.
9. Starts the candidate a second time against the newer fence and requires identity to still report it, the saved evidence and the ledger to be unchanged, and the second child to stop cleanly.
10. Recomputes the binding and requires the artifact inventory, the runtime bytes and the physical release directory to be the ones bound before the run.

If the probing process is interrupted or exits mid-run, an exit and signal guard ends the live candidate's process group, because a retained artifact older than the parent watchdog would otherwise keep running.  If the throwaway home cannot be removed, the run still ends in a `blocked` result and a receipt that names the retained directory.

The receipt is a private JSON file in a directory the caller names outside the release.  It records the physical release, the physical source repository, the source commit, the clean build identity, the artifact and runtime fingerprints, the schema identifier `normalized-v1`, the recipe version, the waits that applied, each outcome and the tail of the child's logs.  The release manifest is read and never written, so it gains no field that an older strict reader would reject.  A receipt grants no authority to migrate, enable a mode, update authentication or prune a rollback generation, and every result carries `activationAllowed: false`.

The cases cover a missing artifact, a mismatched commit, a dirty identity, changed artifact bytes, changed runtime bytes, a scripted, linked or hard-linked runtime, a hard-linked release manifest, a path into a credential, login or dot directory or a dangling link, an identity answer of any size or shape, a replace ref in the source repository, a strict old reader as a negative fixture, normalized fixture success, stale-request and released-lease refusals, a changed logical ledger digest, changed marker, database and WAL bytes, a hold released on DELETE, a candidate that forgets the newer fence on its next boot, shortened or overflowing waits, a retained generation replaced between the probe and the recheck, a child that leaves a descendant holding a loopback port, a home the candidate made undeletable, an interrupted probe, an externally supplied verified report that is ignored, and a signed-bundle candidate that is blocked with a named missing proof.

Recipe version 1 is narrower than the source fixture in these places.  It does not seed a queued delegated assignment or a connected room continuation card, because both need the application store of the tool's own source tree written into the candidate's data directory.  Passive job, scheduler and startup recovery is therefore evidenced only by the unconsumed resumption files, the unchanged ledger and the absent payload namespace.  It does not drive the legacy release-controller and takeover transitions or the regressed-marker 503 that the source fixture checks: the legacy pair is seeded rather than created by the candidate, and only its identity is read back.
Three limits remain open.  Only the retained-release candidate kind is bound: a signed Mac bundle is `blocked` with a named missing proof on every platform, and the Linux server's retained-source closure is `blocked` as an unsupported kind because the plan does not name it.  The fixture writer runs under the tool's own Node while the candidate runs under the selected runtime, so the selected runtime's `node:sqlite` support is exercised by the candidate's reads alone.  BF-2632 stays open: proving an actual built and retained bridge artifact through its shipped runtime, and rechecking retention at the later activation boundary, still needs the owner's decision and partly a Mac.

## The Retained Runtime

The runtime a release runs under is now KEPT, and only a kept runtime can be bound.

A release ships its tree and its node_modules and nothing else: the manifest records `node: process.version`, which is a version string and not bytes.  So the only runtime a candidate could name was one living outside the store — the machine's own node.  Binding that proves the machine's bytes rather than the candidate's, and a node upgrade changes those bytes under a proof that was written against them, so the activation-boundary recheck refuses the release by name.  That refusal is correct for a binding that was never stable, and it means no release can be proved at all.

The store now keeps the bytes.  `retainRuntime` copies a runtime binary into the store's own area, beside `releases/`, `holds/` and `proofs/`, and stores it under its own sha256, so the kept bytes are named by their digest.  The copy is read-only and is never rewritten: an existing file with that name is kept exactly as it is, because a proof records the file's inode as well as its bytes, and replacing the file would replace the very file a proof re-verifies.  A source that is a symlink, a directory, a file without an executable bit or an interpreter script is refused by name.  `bindReleaseRuntime` records which kept runtime a release runs under, in a per-commit record beside the release and never inside it, because the release tree is compared byte for byte with its commit and a file written into it would change the very bytes a proof is about.  The strict manifest keeps exactly its seven fields.

The probe binds only a kept runtime of the store that owns the release: the runtime's directory must be that store's `runtimes` area and the file must be named by its own digest.  The machine's own node is refused with `runtime-not-retained`, and a kept runtime whose bytes no longer match the name it is stored under is refused with `runtime-changed`.  The existing refusals fire first and keep their own names, so a missing, linked, hard-linked, scripted or non-executable runtime is still refused as exactly that.

The always-on launcher prefers the release's bound runtime when the store holds one for it, and keeps the configured `BOTFLEET_NODE` when it does not, so the program that runs a release is the program a proof was written against.  The tracked copy in this repository is what changed; the installed copy on a Mac changes when that Mac installs it.

This is still source-level evidence.  No release has been retained, no runtime has been kept on a live machine, and no activation has been attempted.
