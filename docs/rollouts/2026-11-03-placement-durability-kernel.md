# Transactional Placement Durability

Refs BF-2625.  Builds on BF-2623 and the reviewed private command spool from BF-2604.

## Activation And Rollback Gate

This lands an inactive SQLite correctness kernel.  Ordinary production boots preserve the existing strict JSON epoch authority and its volatile queue contract, creating no SQLite database or payload namespace.  Only an already-activated strict UUID marker selects SQLite.  There is no production API or environment switch for first-time activation.

A later activation unit must verify and retain a rollback build that reads this same SQLite schema and UUID marker before rewriting any production legacy JSON.  Ship and verify that dual-reader bridge while legacy authority remains selected, settle the old volatile placement book, and prove the activation and rollback sequence in isolation before migration.  The installed legacy-only target cannot be used after marker publication.  This source change does not authorize or perform that activation.

Normalized tables now keep recurring row work independent of permanent history.  Indexed scoped reads and targeted writes are implemented for jobs, issuing leases, tombstones and pending stops.  Production activation remains blocked on the verified rollback bridge and the remaining worker, registry and transport acceptance gates.

## Authority And Acknowledgements

Semantically unchanged operations commit without rewriting any job, lease or header row.  Command payloads load only when a specific allocation, dispatch or job query needs them.  Confirmed terminal payload deletion is cached so ordinary heartbeats do not repeatedly read, remove or sync every historical payload.  Existing WAL and SHM entries must be private, owned, regular, single-link files before opening SQLite and during use; the store never follows links or repairs foreign permissions automatically.

The controller uses `placement.sqlite` as one local SQLite authority for the controller pair, reconciliation flag, immutable jobs, original issuing leases, released lease tombstones, pending stops and exact terminal reports.  Each mutation acquires `BEGIN IMMEDIATE`, loads and strictly validates a fresh header, bounded active work and explicit referenced IDs, applies its fence and transition, validates immutable history, then commits before replying.  SQLite runs in local WAL mode with `synchronous=FULL`; an unavailable store or failed write returns no successful acknowledgement.  Read errors, lower observed epochs, unknown schema and malformed relations fail closed.

Worker registrations, admission and last-seen times remain volatile.  Restart requires fresh registration and an admission heartbeat before allocating or replaying a claim.  A lost claim acknowledgement can return only the original issuing lease to the same ready worker; it cannot allocate a replacement lease.  Silence changes leased work to `worker-unreachable` without requeueing it.  Pending stops survive omitted heartbeat lease lists and restart, clearing only with a committed terminal report or a later verified revocation transition.

Takeover commits the new controller, reconciliation flag and orphan markers together.  Each historical lease retains its issuing controller and epoch.  An exact final report from its holding worker may settle that lease after takeover; the old lease cannot authorize a new dispatch or allocation.  Terminal replay compares the complete final result, including an optional reason.  Display hiding never deletes the immutable job or lease/report dedupe history, and the store rejects removal or alteration of execution tombstones.

The current release wire message cannot prove that a worker durably revoked an unstarted lease.  The SQLite backend therefore refuses lease release with a verified-revocation requirement.  The ordinary JSON compatibility backend retains its existing volatile queue contract.  The permanent released-lease schema and delayed-dispatch regression prepare for a later authenticated worker receipt; this slice neither invents that receipt nor accepts a caller boolean as proof.

## Indexed State And Hot Paths

Jobs, immutable issuing leases, irreversible lease tombstones and pending stops occupy separate indexed tables; the controller and reconciliation header stays small.  Controller identity reads only the header.  Heartbeats and decisions load at most the existing 500 unresolved records plus explicit job/lease references.  UI reads add only the existing 20 recent finished-job rows.  Old job IDs, immutable fingerprints, exact final reports and released lease IDs remain indexed lookups after UI hiding; no unloaded history is deleted or rewritten.

Multi-query reads use one consistent SQLite read transaction.  Decisions use `BEGIN IMMEDIATE`, validate the fresh header and active ownership, and insert or update only changed loaded rows.  Epoch changes require the active scope and atomic orphan marking; release verifies that scope is drained.  Complete `readAll` exports and complete-ledger fixture editors remain available for offline audits, but recurring service code never calls them.

All unresolved records, including missing-payload queues held without execution, count against the existing 500-record bound.  The next enqueue refuses before payload publication at capacity.  Fenced maintenance can settle an expired unleased queue item as `lost` with an explicit internal `queueExpiry` disposition, deadline and terminal report, without fabricating an issuing lease.  Durable terminal settlement frees the active slot while retaining its permanent accepted job ID/fingerprint and any previously revoked lease history.  This reuses an existing storage contract rather than adding a resource budget or setting.

The scaling fixture retains 2,000 and then 20,000 historical jobs and performs the same controller, heartbeat, refusal, enqueue, claim, report, cold-ID replay and UI workload.  Both cases return exactly 277 rows across 283 prepared queries and change 6 rows; wall-clock results are logged as secondary evidence.  The fixture also checks indexed ID plans, cold released-lease refusal after UI pruning, and a read snapshot while another writer commits takeover.  The normalized version-one schema explicitly identifies itself as `normalized-v1`; old unreleased snapshot-format fixture databases fail closed rather than being automatically upgraded.

## Private Payloads

Raw commands remain outside SQLite and `jobs.json`, in a separate placement namespace of the reviewed `PendingCommandSpool`.  The copied spool source is byte identical to BF-2604 final reviewed commit `033d2d25`.  Payload publication and directory sync happen under the serialized placement transaction before an enqueue commits.  An interrupted enqueue may leave an orphan payload; startup and subsequent mutations reconcile unreferenced publications and temporary aliases under the SQLite writer lock.  Every unresolved committed reference remains protected, including a payload another writer just claimed.  Conflicting or damaged referenced payloads are preserved and refused rather than silently replaced.

The immutable binding includes job, bot, thread, working directory, timeout and command digest.  Host, controller, lease and wall-clock acceptance time do not bind the command, so a legitimate takeover or same-work retry does not invalidate its payload.  The controller reads payloads without consuming the worker's eventual one-shot launch claim.  Missing or corrupt payloads hold work without reconstructing it from an enqueue or dispatch replay.

The existing 16,000-character command bound and 500-record spool count apply.  Queue expiry reads the existing resolved `queueWaitMinutes` setting, whose reviewed default is 1,440 and range is 1 through 10,080; no new setting is introduced.  Its maintenance transaction verifies the current fence and commits the unleased terminal outcome before raw payload removal.  Enqueue performs maintenance and cleanup first, then a separate fresh fenced admission transaction, so freeing a full spool never requires deleting an uncommitted job's payload or exceeding its existing count.  A failed later admission may leave independent expiry already committed; failed expiry leaves queue metadata and payload intact.  Cleanup failure preserves the terminal fact and blocks new payload publication until writer-locked reconciliation can reclaim storage safely.  Worker messages cannot supply the internal disposition.  No missed heartbeat, execution timeout or queue deadline makes `dispatching`, `running` or `worker-unreachable` work retryable.  Unresolved leases retain their bounded controller payloads because the current heartbeat is not a durable worker receipt.  Full storage blocks new admission rather than pruning execution history.

## Migration And Recovery

Migration runs after existing harness ownership and under the legacy controller writer lock.  It reads the exact private legacy JSON, initializes and syncs a prepared SQLite ledger with that controller and a migration UUID, then atomically publishes and directory-syncs a strict versioned JSON marker carrying the UUID.  Older strict epoch readers reject the marker.  Recovered and active UUID markers repeat their parent directory sync barrier before activation or use; no second live JSON epoch authority remains.

Only a genuinely empty first start initializes epoch zero.  Marker plus missing/mismatched database, missing marker plus an existing database, corrupt data, unknown schema, loose or linked legacy files, mismatched prepared state, and an unexplained legacy JSON beside an active database block startup.  A verified prepared migration can resume from either side of marker publication.  A killed migrator leaves the lock in place and startup never steals it.  Recovery first verifies that every writer has stopped, preserves and verifies the ledger and marker, and removes only the abandoned empty lock before retrying.

Migration cannot reconstruct jobs accepted into an older volatile lease book.  This upgrade precedes enabling real placement execution and must use a settled old placement book.  Preserve the full data directory and use SQLite-consistent backups; copying only a live main database omits its WAL.  The marker deliberately prevents rollback to code that understands only a plain epoch JSON file.  Rolling back code requires this same ledger contract and schema rather than deleting the marker or resetting its epoch.

A live store detects observed epoch regression, and migration rejects a database below its recorded initial fence.  A complete, internally consistent historical database and matching UUID restored after every process stops has no independent monotonic witness in this local design.  This slice does not claim to detect that external rollback; do not restore an older placement backup to evade its fence.
