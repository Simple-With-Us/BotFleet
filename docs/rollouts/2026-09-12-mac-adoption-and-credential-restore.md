## Credential Restore Defect

The desktop passed fixed workspace keys only when spawning a child.  Attachment to the always-on harness replayed custom-instance keys alone, leaving Composio and Infisical unconfigured despite retained project/session identifiers.  Issue #329 adds an owner-authenticated, loopback-only restore operation separate from settings edits.  It accepts only fixed credential names, retains existing resolved config and canonical Infisical values, writes no plaintext config or vault values, and refuses active work before mutation.  A synchronous provider fence protects accepted restoration; repeated attachment is idempotent.  The desktop retries from its current encrypted store after work finishes and stops retrying on quit.

Custom-instance keys now use the same authenticated idle guard before a targeted provider refresh.  The old replay could interrupt active turns through the ordinary settings route.  Restoration holds the existing encrypted-document transaction, so a later successful clear or save cannot race an older replay; only a confirmed missing instance removes its stale encrypted key.  Request deadlines and generic diagnostics avoid forwarding secrets through redirects or error text.  CLI version probes now use the shared workspace and provider credential filters, so restored DeepSeek and Infisical credentials cannot reach an operator-selected wrapper.

The startup race is closed at both owners of the credential boundary.  `electron/credential-restore.mjs` derives custom-instance IDs and fixed workspace credential presence from the encrypted document and writes only durable `credentialStorage: "external"` markers.  Interactive turns, room members, queued fallback, boot recovery, routines, and direct fixed-credential consumers wait only when their selected credential is marked but has not been restored; anonymous and unrelated engines remain available.  Initial authenticated replay is awaited before the renderer is created.  Each marker contains no key, account data, or fingerprint.

The permanent updater invokes the installed candidate's dedicated credential-preparation mode after the old desktop stops and before the detached harness restarts.  That mode initializes no window, Sentry client, server, or provider consumer.  It reads the existing encrypted document, writes and strictly reads back every required nonsecret marker, and emits a private receipt bound to the candidate source commit.  It deliberately does not migrate or delete legacy plaintext secrets, so a later rollback can still start the old harness with the credential material it previously understood.

`server/index.ts` treats a marked credential with no restored runtime override as credential-pending.  Interactive sends return 409, while room rounds, fallback turns, boot recovery, and routines retain their original work until restore.  Crash recovery retains the original `inflightThreadId`, and `server/routines.ts` leaves routine receipts queued without creating or activating empty tasks.  An authenticated restore may ignore only those inert credential-waiting queues for its idle decision, but active turns, running or waiting routines, concurrent admissions, reloads, and every other existing readiness category still block it.  Provider mutation fences routine admission synchronously; after restore, the harness retries each retained operation once.
